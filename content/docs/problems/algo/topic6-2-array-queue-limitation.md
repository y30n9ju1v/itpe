## 문제

## 모범답안

1. 배열 기반 큐(Linear Queue)의 개요

    정 의  • 배열 인덱스를 이용해 Front/Rear 포인터로 Enqueue/Dequeue를
             관리하는 가장 단순한 큐 구현 방식
           - 정적 연속 메모리 위에 FIFO를 구현하여 구조적 한계 내재

    ```
    초기:  [   ][   ][   ][   ][   ]     Front=Rear=0
    Enqueue(A,B,C): [ A ][ B ][ C ][   ][   ]   Front=0, Rear=3
    Dequeue() x2  : [   ][   ][ C ][   ][   ]   Front=2, Rear=3
                      ↑↑↑ 사용 불가 공간(낭비) 발생
    ```

    - Rear가 배열 끝에 도달하면 앞쪽 빈 공간이 있어도 Enqueue 불가한 문제 발생.

2. 배열 기반 큐의 단점

    | 단점 | 원인 | 영향 |
    |------|------|------|
    | 가공 오버플로우 | Dequeue로 비워진 앞쪽 공간 미재사용 | 여유 공간 있어도 Enqueue 실패 |
    | 고정 크기(정적 할당) | 배열 크기가 초기화 시 고정 | 데이터량 예측 실패 시 진짜 Overflow |
    | 중간 삽입/삭제 시 원소 이동 | 인덱스 연속성 유지 필요 | O(n) 비용, 성능 저하 |

    - "선형 배열 큐를 그대로 운영 환경에 적용"하는 것은 실무 안티패턴.

3. 해결 방법 비교

    1) 해결 방법 3가지

    ```
    순환 큐  : Rear=(Rear+1)%Capacity  → 앞쪽 공간 재사용
    연결리스트 큐 : 노드 단위 동적 할당 → 고정 크기 제약 제거
    동적 배열 큐  : 포화 시 2배 재할당(Resize) → 상환 O(1) 성능 유지
    ```

    2) 해결 방법 비교표

    | 해결 방법 | 오버플로우 해결 | 구현 복잡도 | 적합 상황 |
    |-----------|------------------|--------------|-----------|
    | 순환 큐 | 가공 오버플로우 해결 | 낮음(모듈러 연산) | 용량 예측 가능한 임베디드/버퍼 |
    | 연결리스트 큐 | 완전 해결 | 중간(포인터 오버헤드) | 데이터량 변동 폭 큰 애플리케이션 |
    | 동적 배열 큐 | 재할당으로 해결 | 중간(일시적 2배 메모리) | 상환 성능 중요한 범용 라이브러리 |

4. 실무 적용 방안

    | 이슈 | 대응방안 |
    |------|----------|
    | 학습용 선형 큐를 검증 없이 운영 적용 | 검증된 큐 구현체(ArrayDeque 등) 우선 채택 |
    | 순환 큐도 단일 프로세스 Capacity 한계 존재 | 대규모 스트리밍은 Kafka·RabbitMQ 분산 메시지 큐 도입 |
    | 연결리스트 큐의 캐시 지역성 저하 | 메모리 풀/세그먼트 큐 구조로 성능 보완 |

    - 최근 분산 메시지 큐(Kafka 등) 기반 이벤트 스트리밍 아키텍처 적용 증대 예상.  "끝"
