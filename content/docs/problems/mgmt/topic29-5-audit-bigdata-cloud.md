## 해설

### 출제 배경 및 의도

전통적인 감리기준은 구조적/객체지향 개발모델을 전제로 설계되어, 빅데이터 파이프라인이나 클라우드 네이티브 아키텍처처럼 데이터 중심·인프라 추상화가 심화된 사업에는 그대로 적용하기 어렵다. 예컨대 빅데이터 사업은 "데이터 품질과 파이프라인 신뢰성"이 핵심 리스크인데 기존 감리 체크리스트는 이를 다루지 못했고, 클라우드 사업은 "물리 자원이 아닌 서비스 계약과 공유 책임 모델"을 점검해야 하는데 기존 감리기준은 온프레미스 인프라를 전제로 했다.

이에 NIA는 "지능정보기술 감리 실무 가이드"를 통해 빅데이터·클라우드·AI 등 신기술 영역에 특화된 감리 점검항목을 별도 제시하고 있다. 이 문제는 데이터 경제·클라우드 전환이라는 최신 IT 트렌드 속에서 감리 방법론이 어떻게 진화하고 있는지를 묻는 최신형 문제로, 향후 출제 빈도가 높아질 것으로 예상되는 영역이다.

### 1. 지능정보기술 감리 실무 가이드 개요

정 의  • 빅데이터·클라우드·AI 등 지능정보기술 기반 사업의 특성을 반영하여 기존 감리기준을 보완하는 특화 점검 가이드(NIA 발간)
       - 전통적 SDLC 산출물 점검 방식만으로는 데이터 파이프라인 품질, 클라우드 서비스 계약 적정성을 점검할 수 없다는 문제의식에서 출발.

```
[기존 감리기준의 한계와 지능정보기술 가이드의 보완]
기존 감리기준: 요구사항→설계→구현→시험 (SW 코드 중심)
      │
      ▼ 보완 필요 영역
빅데이터 사업: 데이터 수집→저장→처리→분석→활용 (데이터 파이프라인 중심)
클라우드 사업: 서비스 선정→구성→마이그레이션→운영 (서비스 계약/공유책임 중심)
```

### 2. 가. 빅데이터 감리 점검 단계

| 점검 단계 | 점검 내용 |
|---------|---------|
| ① 데이터 수집 단계 | 데이터 출처 신뢰성, 수집 방식(배치/스트리밍) 적정성, 개인정보 비식별화 |
| ② 데이터 저장 단계 | 데이터 레이크/웨어하우스 설계 적정성, 스키마 온 리드(Schema-on-Read) 전략 |
| ③ 데이터 처리 단계 | ETL/ELT 파이프라인 무결성, 분산처리(Hadoop/Spark) 구성 적정성 |
| ④ 데이터 분석 단계 | 분석 모델 검증, 알고리즘 편향(Bias) 점검 |
| ⑤ 데이터 활용/서비스 단계 | 시각화·API 제공의 데이터 정합성, 활용 목적 부합성 |
| ⑥ 데이터 품질/거버넌스 | 데이터 품질관리체계(정확성/일관성/최신성), 메타데이터 관리 |

```
[빅데이터 파이프라인 감리 흐름]
수집(Source) → 저장(Lake/DW) → 처리(ETL/ELT) → 분석(모델링) → 활용(서비스)
   감리①          감리②           감리③           감리④        감리⑤
                                     └── 전 단계 공통: 데이터 품질/거버넌스 감리⑥
```

- 기존 SW개발 감리와 달리 "코드 품질"보다 "데이터 품질(정확성, 일관성, 완전성, 적시성)"이 핵심 감리영역이며, 데이터 리니지(Lineage) 추적 가능성이 중요한 점검 포인트이다.

### 3. 나. 클라우드 감리 점검 단계

| 점검 단계 | 점검 내용 |
|---------|---------|
| ① 클라우드 서비스 선정 | 서비스모델(IaaS/PaaS/SaaS) 적정성, 사업자 보안인증(CSAP) 확인 |
| ② 아키텍처 설계 | 가용영역(AZ) 이중화, 오토스케일링, 네트워크 격리 설계 |
| ③ 마이그레이션 | 데이터/시스템 이전 계획, 다운타임 최소화 전략, 롤백 계획 |
| ④ 보안/공유책임 | 클라우드 공유책임모델(CSP vs 이용기관 책임 범위) 준수 |
| ⑤ 운영/비용관리 | 오토스케일링 정책 적정성, 비용 최적화(FinOps), 모니터링 체계 |
| ⑥ 종속성/이식성 | 벤더 락인(Lock-in) 위험도, 멀티클라우드/이식성 확보 방안 |

```
[클라우드 사업 감리 흐름]
서비스 선정(IaaS/PaaS/SaaS) → 아키텍처 설계(이중화/네트워크)
   → 마이그레이션(다운타임 관리) → 보안(공유책임모델)
   → 운영(비용/모니터링) → 종속성 관리(Lock-in 회피)
```

```
[클라우드 공유책임모델(Shared Responsibility Model)]
IaaS : CSP(하드웨어/가상화) | 이용기관(OS/미들웨어/애플리케이션/데이터)
PaaS : CSP(하드웨어~런타임)  | 이용기관(애플리케이션/데이터)
SaaS : CSP(전 계층 대부분)   | 이용기관(데이터/사용자 접근관리)
─ 감리 핵심: 이용기관이 "자신의 책임 범위"를 명확히 인지하고 이행하는지 점검
```

### 4. 빅데이터 감리와 클라우드 감리의 비교

| 구분 | 빅데이터 감리 | 클라우드 감리 |
|------|-------------|-------------|
| 핵심 리스크 | 데이터 품질, 개인정보, 알고리즘 편향 | 벤더 락인, 공유책임 오인, 비용 폭증 |
| 감리 포인트 이동 | 코드 → 데이터 파이프라인 | 인프라 소유 → 서비스 계약/구성 |
| 특화 점검 항목 | 데이터 리니지, 메타데이터 관리 | 공유책임모델, FinOps |

- 빅데이터 감리는 데이터 자체의 품질·윤리성에, 클라우드 감리는 서비스 계약과 책임 범위 획정에 각각 초점을 두어야 하며, 두 영역 모두 전통적 코드 중심 감리에서 데이터·계약 중심 감리로 무게중심이 이동하고 있다.  "끝"

### 실무 제언

**데이터 리니지 추적 체계 미비**
- **챌린지**: 빅데이터 파이프라인은 다단계 변환을 거치므로, 최종 분석 결과가 어떤 원천 데이터에서 왔는지 추적이 어려워 감리 시 데이터 무결성 검증이 곤란하다.
- **제언**: 데이터 리니지 관리 도구(메타데이터 카탈로그)를 파이프라인 구축 초기부터 의무화하고, 감리 점검항목에 리니지 추적 가능성을 명시적으로 포함해야 한다.

**클라우드 공유책임모델에 대한 발주기관의 오해**
- **챌린지**: 공공기관이 클라우드 도입 시 "클라우드 사업자가 보안을 전부 책임진다"고 오인하여 자신의 책임 영역(접근권한 관리, 데이터 암호화 설정)을 소홀히 하는 사고가 빈번하다.
- **제언**: 감리 착수 단계에서부터 서비스모델(IaaS/PaaS/SaaS)별 공유책임 경계를 명문화한 문서를 발주기관에 제출받고, 이용기관 책임 영역의 이행 여부를 집중 점검해야 한다.

**벤더 락인 위험과 이식성 확보**
- **챌린지**: 특정 클라우드 사업자의 독자 관리형 서비스(Managed Service)에 과도하게 의존하면, 향후 사업자 변경이나 재입찰 시 막대한 전환 비용이 발생한다.
- **제언**: 감리 시 컨테이너화(Kubernetes)·표준 API 사용 여부를 점검하여 이식성을 사전에 확보하도록 권고하고, 장기적으로 멀티클라우드 전략 수립 여부를 감리 개선권고에 반영해야 한다.
