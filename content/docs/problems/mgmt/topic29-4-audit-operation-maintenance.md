## 해설

### 출제 배경 및 의도

공공 정보시스템 대란(예: 행정전산망 장애)이 반복될 때마다 "왜 사전에 발견하지 못했는가"라는 질문이 제기된다. 개발 감리는 신규 구축 시스템에 집중되어 있지만, 이미 운영 중인 시스템의 장애 위험은 운영·유지보수 단계의 관리 소홀에서 비롯되는 경우가 대다수다. 이에 정보시스템 감리기준은 개발 감리와 별도로 "운영 감리"와 "유지보수 감리"를 사업유형으로 명시하고 있다.

이 문제는 "장애 예방"이라는 최신 이슈와 감리 제도를 연결짓는 문제로, 응시자가 운영 감리(인프라·서비스 가용성 관점)와 유지보수 감리(변경관리·형상관리 관점)를 구분하여 설명할 수 있는지를 검증한다. 개발 감리와 달리 운영·유지보수 감리는 "이미 살아있는 시스템"을 대상으로 하므로 서비스 중단 없이 점검해야 하는 특수성이 있다는 점도 중요한 포인트다.

### 1. 가. 시스템 운영, 유지보수 감리의 개념

정 의  • 시스템 운영 감리는 이미 구축되어 서비스 중인 정보시스템의 운영 체계(인프라, 서비스 수준, 보안)의 적정성을 점검하는 감리이다.
       • 유지보수 감리는 운영 중인 시스템에 대한 변경(기능개선, 결함수정)이 적절한 절차와 품질기준을 준수하며 이루어지는지를 점검하는 감리이다.

```
[개발 감리 vs 운영/유지보수 감리]
개발 감리   : 신규 시스템 구축 과정(요구→설계→구현→시험) 점검
운영 감리   : 이미 가동 중인 시스템의 "현재 상태" 점검(정적 관점)
유지보수 감리: 가동 중인 시스템에 가해지는 "변경 행위" 점검(동적 관점)
```

| 구분 | 운영 감리 | 유지보수 감리 |
|------|---------|-------------|
| 대상 | 운영 중인 시스템 자체 | 시스템에 대한 변경 활동 |
| 관점 | 정적(현재 상태의 적정성) | 동적(변경 프로세스의 적정성) |
| 목적 | 장애 예방, 서비스 안정성 확보 | 변경으로 인한 품질 저하·오류 방지 |
| 점검 시점 | 정기(연 1~2회) 또는 상시 | 유지보수 계약 기간 중 수시 |

### 2. 나. 시스템 운영 감리의 점검분야

| 점검분야 | 세부 점검 항목 |
|---------|-------------|
| 운영 조직/체계 | 운영 인력 배치, 역할분담(R&R), 비상연락체계 |
| 인프라 안정성 | 서버/네트워크/스토리지 용량, 이중화 구성, 노후장비 현황 |
| 서비스 수준 관리 | SLA 준수율, 응답시간, 가용성(Availability) 목표 대비 실적 |
| 보안 관리 | 접근통제, 취약점 점검 이력, 개인정보 처리 현황 |
| 백업/복구 체계 | 백업 주기, 복구 테스트 이력, DRS 구성 |
| 장애 관리 | 장애 이력관리, 근본원인분석(RCA), 재발방지대책 이행 여부 |

```
[운영 감리 점검 프로세스]
운영현황 자료 수집(SLA 실적, 장애이력, 백업로그)
        │
        ▼
현장 점검(인프라 구성도 대사, 이중화 상태 확인)
        │
        ▼
인터뷰(운영조직 R&R, 비상대응 체계 확인)
        │
        ▼
개선권고(노후장비 교체, 백업주기 조정 등)
```

### 3. 다. 유지보수 감리의 점검분야

| 점검분야 | 세부 점검 항목 |
|---------|-------------|
| 변경관리 프로세스 | 변경요청(CR) 접수·승인·이행 절차 준수 여부 |
| 형상관리 | 소스코드/문서 버전관리, 기준선 관리, 변경이력 추적성 |
| 품질보증 | 변경 후 회귀시험(Regression Test) 수행 여부 |
| 유지보수 계약 이행 | 계약 범위 대비 실제 수행 내역 일치 여부, 대가 지급 적정성 |
| 문서 갱신 | 매뉴얼·설계서 등 관련 문서의 변경사항 반영 여부 |
| 하도급 관리 | 유지보수 하도급 시 적정 대가 지급, 품질 관리 여부 |

```
[유지보수 감리 점검 흐름]
변경요청(CR) 발생 → 영향분석 → 변경승인(CCB)
   → 변경수행(코드+문서) → 회귀시험 → 형상관리 반영(기준선 갱신)
        │
        └─ 감리는 각 단계의 절차 준수와 산출물 추적성(CR ID ↔ 커밋 ↔ 시험결과)을 점검
```

- 유지보수 감리의 핵심은 "작은 변경이 누적되어 시스템 전체 아키텍처를 훼손하지 않는지"를 확인하는 것이며, 이는 개발 감리의 1회성 점검과 달리 지속적·반복적 점검 체계를 요구한다.  "끝"

### 실무 제언

**운영 감리의 정기성 확보**
- **챌린지**: 운영 감리는 법적 의무가 아닌 경우가 많아 발주기관이 예산·인력 부담을 이유로 생략하거나 형식적으로 진행하는 경우가 많다.
- **제언**: 정보시스템 등급(주요정보통신기반시설 등)에 따라 운영 감리를 정기 의무화하고, 장애 이력이 있는 시스템은 우선순위를 높여 집중 점검하는 위험기반 접근을 적용해야 한다.

**유지보수 변경의 누적 리스크(아키텍처 부식)**
- **챌린지**: 개별 유지보수 건은 작고 사소해 보이지만, 장기간 누적되면 당초 설계 원칙이 훼손되어 "기술 부채"가 쌓이고 결국 대형 장애로 이어진다.
- **제언**: 유지보수 감리에 "누적 변경 이력 분석"을 정기 점검항목으로 포함시켜, 특정 모듈에 변경이 집중되는 경우 구조적 리팩토링을 권고하는 예방적 감리를 수행해야 한다.

**클라우드 환경에서의 운영 감리 방식 전환**
- **챌린지**: 온프레미스 중심으로 설계된 기존 운영 감리 점검항목(물리 서버, 이중화 등)은 클라우드 네이티브 환경(오토스케일링, 매니지드 서비스)에 그대로 적용하기 어렵다.
- **제언**: 클라우드 환경에서는 IaC(Infrastructure as Code) 형상 이력, 오토스케일링 정책, 클라우드 비용 최적화까지 포함하는 클라우드 특화 운영 감리 체크리스트로 전환해야 한다.
