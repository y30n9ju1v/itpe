## 해설

### 출제 배경 및 의도

"우리 회사는 왜 늘 헐값에 야근하며 추가 개발을 해줘야 하는가?" 공공 SW사업 현장에서 개발자들이 자조적으로 던지는 이 질문의 근본 원인이 바로 불합리한 과업변경 관행이다. 발주기관은 예산 부족·요구사항 미확정 등을 이유로 계약범위를 벗어난 추가요구를 관행적으로 무상 처리해왔고, 수행사는 계약 유지·평판 관리를 위해 이를 수용해온 구조적 문제가 있었다.

이에 과학기술정보통신부는 2020년 "공공 소프트웨어사업 과업변경 관리 가이드"를 배포하여 과업변경의 판단기준·절차·대가산정 근거를 명문화했다. 이 문제는 SW생태계의 고질적 병폐인 '갑을관계형 과업변경'을 얼마나 구조적으로 이해하고, 제도적 해법(권고기준·절차)을 설명할 수 있는지를 검증한다. 최근 대가지급 지연 문제, 하도급 부조리와 함께 SW산업 공정화의 핵심 축으로 계속 출제되는 주제이다.

### 1. 과업변경의 개념과 기존 문제점

정 의  • 과업변경이란 계약 체결 후 사업 범위·내용·일정 등 계약사항을 변경하는 것으로, 사업 수행 중 불가피하게 발생하는 요구사항 추가·변경·삭제를 의미한다.
       - 문제는 "정당한 대가 없는 일방적 과업변경(공짜 야근/추가개발)"이 관행화되었다는 점이다.

가. 기존 과업변경의 문제점

| 문제 유형 | 세부 내용 | 원인 |
|---------|---------|------|
| 판단기준 부재 | 계약범위 내/외 여부를 판단할 객관적 기준 없음 | RFP·SIRS 요구사항 명세 미흡 |
| 대가 미지급 관행 | 변경 발생 시 무상 처리 요구가 관행화 | 발주기관 우월적 지위, 예산 경직성 |
| 협의체 부재 | 발주자-수행사 간 공식 협의·조정 채널 없음 | 담당자 개인 재량에 의존 |
| 서면화 미흡 | 구두 지시로 과업변경이 이루어져 분쟁 시 입증 곤란 | 변경관리 프로세스 미정립 |
| 하도급 전이 | 원사업자가 부담을 하도급업체에 전가 | 다단계 하도급 구조 |

```
[기존 과업변경의 악순환 구조]
발주기관 요구사항 모호 → 수행 중 추가요구 발생 → 판단기준 없음
   → 수행사 "관계 유지" 위해 무상 수용 → 원가 손실 → 하도급 전가
   → 품질 저하·납기 지연 → 갈등 심화 (반복)
```

### 2. 나. 적정 과업변경 판단 권고기준

과기정통부 가이드는 아래 4가지 기준으로 "정당한 과업변경"과 "계약범위 내 이행사항"을 구분하도록 권고한다.

| 판단기준 | 설명 | 예시 |
|---------|------|------|
| ① 계약목적 부합성 | 원 계약의 목적·범위를 벗어나는지 여부 | RFP상 명시 안 된 신규 기능 요구 |
| ② 요구사항 명확성 | RFP/SIRS에 명시되지 않은 요구인지 | "~정도"의 모호한 표현으로 추가 해석 필요한 경우 |
| ③ 기술적 난이도 변화 | 당초 예정 공수 대비 현저한 증가 여부 | 아키텍처 재설계 수준의 변경 |
| ④ 원인 제공자 | 발주기관 요구/환경변화 vs 수행사 귀책 | 법령 개정, 정책 변경으로 인한 요구 추가 |

```
[판단 흐름도]
신규/변경 요구 발생
        │
        ▼
  RFP/SIRS에 명시? ──Yes──▶ 계약범위 내 이행 (과업변경 아님)
        │No
        ▼
  계약목적 범위 내? ──No──▶ 과업변경 대상(대가 재산정)
        │Yes(단, 난이도 급증)
        ▼
   기술난이도 현저 증가? ──Yes──▶ 과업변경 대상(공수 재산정)
```

### 3. 다. 과업변경 절차

| 단계 | 활동 | 산출물 |
|------|------|-------|
| ① 변경요청 접수 | 발주기관/수행사 누구나 서면으로 변경요청서 제출 | 과업변경요청서 |
| ② 영향도 분석 | PM/PMO가 일정·비용·품질에 미치는 영향 분석 | 영향분석보고서 |
| ③ 협의·심의 | 과업변경심의위원회(또는 CCB) 검토 및 승인 여부 결정 | 심의결과서 |
| ④ 대가 산정 | 기능점수(FP) 등 객관적 기준으로 증감 공수·금액 산정 | 대가산정내역서 |
| ⑤ 계약변경 | 계약서·과업내용서 갱신, 정식 계약 변경 체결 | 변경계약서 |
| ⑥ 이행·기록 | 변경사항 반영 수행, 형상관리 및 이력관리 | 변경이력대장 |

```
[과업변경 절차 흐름]
변경요청 → 영향분석 → 심의위원회 → 대가산정(FP기반)
    → 계약변경 체결 → 이행 및 형상관리 반영
```

- 핵심은 "말로 하지 말고 서면으로, 무상이 아니라 대가산정 근거를 갖고" 진행하는 것이며, 기능점수(Function Point)나 SW사업대가기준을 활용해 변경 공수를 정량화하는 것이 권고된다.  "끝"

### 실무 제언

**모호한 요구사항이 낳는 분쟁의 씨앗**
- **챌린지**: RFP 단계의 요구사항이 정성적으로 서술되면 수행 단계에서 "이 정도는 당연히 포함"이라는 해석 차이가 발생한다.
- **제언**: 계약 체결 전 SIRS 기반 요구사항추적표(RTM)를 발주기관과 공동 확정하여, 향후 과업변경 여부 판단의 객관적 근거로 삼아야 한다.

**PMO/감리와 과업변경 심의의 연계**
- **챌린지**: 과업변경 심의위원회가 형식적으로 운영되어 발주기관 담당자의 일방적 결정으로 귀결되는 경우가 많다.
- **제언**: PMO가 영향분석 단계에 참여하여 객관적 근거자료(FP 산정, 일정 영향)를 제공하고, 감리는 사후 형상관리 준수 여부를 점검함으로써 절차의 실효성을 높여야 한다.

**대가기준의 표준화 필요성**
- **챌린지**: 변경 공수 산정 기준이 사업마다 상이하여 발주기관과 수행사 간 금액 협상이 소모전으로 흐른다.
- **제언**: SW사업 대가산정 가이드(기능점수 기반)를 계약서에 사전 명시하여, 변경 발생 시 분쟁 없이 즉시 산정식에 대입할 수 있는 구조를 마련해야 한다.
