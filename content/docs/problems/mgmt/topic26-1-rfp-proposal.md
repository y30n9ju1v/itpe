## 문제

"소프트웨어산업진흥법"은 공공정보화사업에 대하여 요구사항을 명확하고 상세하게 제안요청서(RFP)를 작성하도록 의무화하였다. 공공정보화 사업 유형이 정보화프로젝트관리서비스(PMO) 사업을 준비하는 경우, 다음에 대하여 작성하시오.

- 가. RFP의 목차 구성
- 나. 제안요청내용 중 필수 요구사항

## 해설

### 출제 배경 및 의도

공공정보화 사업의 실패 원인 1위는 예나 지금이나 "모호한 요구사항"이다. 발주기관이 무엇을 원하는지 제안요청서(RFP: Request For Proposal)에 명확히 담지 못하면, 수행사는 최소 사양으로 응찰하고 이후 과업범위 분쟁(Scope Creep)이 반복된다. 이에 소프트웨어산업진흥법 및 관련 고시는 RFP 작성을 의무화하고 표준 목차·요구사항 명세 형식(SIRS)을 제시하고 있다.

특히 이 문제는 사업 유형을 "PMO(정보화프로젝트관리서비스)"로 특정하고 있다는 점이 핵심이다. PMO 사업은 시스템 개발이 아니라 관리·감독 용역이므로, 일반 SW개발 RFP와 달리 기능 요구사항보다 관리 요구사항(품질/보안/사업관리)의 비중이 압도적으로 높다. 채점관은 응시자가 RFP의 표준 목차를 암기하는 수준을 넘어, PMO라는 특수한 사업 성격에 맞게 필수 요구사항을 재구성할 수 있는지를 검증한다.

### 1. RFP(제안요청서) 개요

정 의  • 발주기관이 사업목적·범위·요구사항·평가기준을 명시하여 제안서 작성을 요청하는 공식 문서
       - 소프트웨어산업진흥법 제20조의2에 따라 공공 SW사업은 RFP 작성이 의무이며, 요구사항은 SIRS(소프트웨어 요구사항 명세서) 형식을 따른다.

```
[RFP 작성·활용 흐름]
사업계획 수립 → 정보화전략계획(ISP) → RFP 작성 → 사전규격공개
     → 제안요청 공고 → 제안서 접수/평가(기술+가격) → 협상 → 계약 체결
```

- RFP 품질이 낮으면 제안서 품질도 낮아지고, 결국 계약 이후 과업범위 다툼으로 이어지는 악순환 구조를 갖는다.

### 2. 가. RFP의 목차 구성

| 대분류 | 세부 목차 | 핵심 내용 |
|-------|---------|---------|
| I. 사업 개요 | 사업명, 목적, 배경, 기간, 예산 | 사업 추진 배경과 범위의 큰 그림 |
| II. 추진 계획 | 사업 범위, 추진체계, 일정(WBS) | 발주기관·수행사 역할분담 |
| III. 제안요청 내용 | 기능/성능/시스템/데이터/보안 요구사항 | SIRS 기준 요구사항 명세(고유번호 부여) |
| IV. 사업관리 요구사항 | 프로젝트관리, 품질보증, 형상관리 | PMO/감리 연계 방안 |
| V. 제안서 작성 지침 | 제안서 목차, 분량, 제출방법 | 공정경쟁 보장을 위한 형식 통일 |
| VI. 평가 기준 | 기술평가/가격평가 배점표 | 정성·정량 평가 항목과 가중치 |
| VII. 계약 조건 | 대가지급, 하자보수, 지식재산권 | 표준 용역계약 특수조건 반영 |

```
[SIRS 요구사항 식별체계 예시]
SFR-001  기능 요구사항(Software Functional Requirement)
SPR-001  성능 요구사항(Performance)
SSR-001  보안 요구사항(Security)
SQR-001  품질 요구사항(Quality)
SIR-001  인터페이스 요구사항(Interface)
SCR-001  데이터 요구사항(Data/Convert)
SMR-001  관리 요구사항(Project Management)
```

### 3. 나. PMO 사업 제안요청내용 중 필수 요구사항

PMO 사업은 "SW를 개발"하지 않고 "개발을 관리·감독"하는 용역이므로, 일반 SI RFP와 요구사항 구성의 무게중심이 다르다.

| 구분 | 일반 SI 개발 RFP | PMO 사업 RFP (본 문제 특성) |
|------|----------------|--------------------------|
| 중심 요구사항 | 기능 요구사항(SFR) 최다 | 관리 요구사항(SMR) 최다 |
| 산출물 | 소스코드, 시스템 | 점검보고서, 개선권고서, 이슈로그 |
| 평가 포인트 | 기술 아키텍처 역량 | PM 경력, 방법론 이해도, 독립성 |
| 필수요구사항 예 | 성능/보안 요구사항 | 사업관리 통제 요구사항 |

PMO 사업 RFP의 필수 요구사항 5대 영역:

1) **사업관리 지원 요구사항** — 일정/범위/품질/위험 관리 계획 검토 및 개선 권고, 정기 보고 체계
2) **기술지원 요구사항** — 아키텍처 적정성 검토, 요구사항 변경 영향분석 지원
3) **품질/성능관리 요구사항** — 테스트 계획 검토, 결함관리, 성능 목표 대비 점검
4) **위험/이슈관리 요구사항** — 리스크 조기경보(Early Warning), 이슈 에스컬레이션 절차
5) **독립성/윤리 요구사항** — 발주기관·수행사로부터의 이해상충 배제, 겸업 제한 조항

```
[PMO 필수요구사항 구조도]
발주기관 ── 계약 ── PMO
              │
              ├─ 사업관리 지원 (일정/범위/품질/위험)
              ├─ 기술지원 (아키텍처/변경영향)
              ├─ 품질관리 (테스트/결함)
              └─ 독립성 확보 (이해상충 배제)
                              │
                         수행사(SI) 감독/조정
```

- PMO는 감리와 달리 "상시 관리·조정" 역할이므로, RFP에는 감리와의 역할 중복을 배제하는 명확한 업무분장 요구사항이 반드시 포함되어야 한다.  "끝"

### 실무 제언

**모호한 요구사항으로 인한 과업범위 분쟁**
- **챌린지**: RFP의 요구사항이 "~를 지원해야 한다" 식의 정성적 서술에 그치면, 수행 단계에서 발주기관과 수행사 간 해석 차이로 과업변경 분쟁이 발생한다.
- **제언**: SIRS 표준 양식에 따라 요구사항마다 고유 ID·상세 설명·산출물·검수기준을 명시하고, 요구사항추적표(RTM)로 계약 산출물과 1:1 매핑되도록 관리해야 한다.

**PMO와 감리의 역할 혼선**
- **챌린지**: 실무에서는 PMO와 감리가 유사한 점검 활동을 수행하여 발주기관이 이중 비용을 지불하거나, 반대로 역할 공백이 발생하는 경우가 많다.
- **제언**: RFP 작성 단계에서부터 PMO는 "상시·선제적 관리 지원", 감리는 "독립적·사후적 품질 검증"으로 역할을 명문화하고, 정기 협의체를 통해 정보를 공유하되 의사결정 권한은 분리해야 한다.

**사전규격공개 제도의 활용**
- **챌린지**: RFP 확정 후 공고하면 특정 업체에 유리한 스펙(벤더 록인)이 뒤늦게 발견되어도 수정이 어렵다.
- **제언**: 나라장터 사전규격공개 제도를 통해 RFP 초안을 일정 기간 공개하고 잠재 참여업체의 이의제기를 반영함으로써 공정경쟁성과 요구사항 완성도를 동시에 높일 수 있다.
