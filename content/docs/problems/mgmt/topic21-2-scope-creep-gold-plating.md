## 해설

### 출제 배경 및 의도

국내 SI 프로젝트가 만성적인 저품질·지연·초과예산에 시달리는 근본 원인 중 하나는 공식적인 변경통제 절차를 거치지 않고 범위가 슬금슬금 늘어나는 현상, 즉 "밑도끝도 없는 요구사항 추가"에 있다. 발주기관의 잦은 요구사항 변경(Scope Creep)과, 개발자·PM이 스스로 만족을 위해 요구되지 않은 기능까지 얹는 관행(Gold Plating)은 겉보기엔 상반된 주체(고객 vs 공급자)에서 발생하지만 결과적으로 동일하게 프로젝트를 실패로 이끈다는 공통점이 있다.

21-1이 WBS를 통한 범위의 '구조화·활용'에 초점을 둔다면, 이 문제는 범위 통제가 실패하는 두 가지 전형적 병리 현상과 그 대응방법을 물어, 범위관리의 '방어적' 측면(왜 범위가 무너지는가, 어떻게 막을 것인가)을 검증한다. 채점관은 두 개념의 발생 주체·동기의 차이를 명확히 구분하고, 각각에 맞는 차별화된 대응 전략을 제시하는지를 중점적으로 평가한다.

### 1. Scope Creep과 Gold Plating의 개념

정 의  • Scope Creep(범위 크리프)은 공식적인 변경통제 절차 없이 고객·이해관계자의 요구에 따라 프로젝트 범위가 점진적으로 확대되는 현상을 의미한다.
       • Gold Plating(금도금)은 공급자(개발팀)가 고객이 요구하지 않은 기능이나 품질 수준을 자발적으로 추가하는 현상을 의미한다.

```
[두 현상의 발생 구조 비교]

Scope Creep                          Gold Plating
고객 요구 증가                       개발자 자발적 추가
   │                                    │
"이것도 해주세요" (요청)              "이왕이면 이것도" (자의)
   │                                    │
비공식 승인 → 범위 통제 실패          불필요 기능 → 리소스 낭비
   │                                    │
    ▼                                    ▼
   납기 지연, 예산 초과, 품질 저하 (공통 결과)
```

### 2. 개념 비교 및 발생 원인

| 구분 | Scope Creep | Gold Plating |
|------|-------------|---------------|
| 발생 주체 | 고객/이해관계자 | 개발팀/PM 자신 |
| 발생 동기 | 요구사항 추가 압박, 명확화 미흡 | 고객 만족도 제고, 기술적 과시욕 |
| 통제 절차 | 우회(비공식 요청 수용) | 통제 대상 자체가 아님(자발적 행위) |
| 대표 증상 | "이왕 하는 김에 이것도 추가해주세요" | "요청하지 않았지만 이 기능도 넣었습니다" |
| 주요 원인 | 초기 요구사항 정의 미흡, 명확한 승인 절차 부재 | 품질 만족 욕구, 범위 통제 인식 부족, 과잉 엔지니어링 |
| 공통 결과 | 일정 지연, 비용 초과, 품질 저하, 팀 소진(burnout) |

### 3. 대응방법

1) Scope Creep 대응방법

| 대응 방안 | 내용 |
|---------|------|
| 명확한 범위기술서(Scope Statement) 작성 | 프로젝트 착수 시점에 범위 경계를 문서로 명확화 |
| 변경통제위원회(CCB) 운영 | 모든 요구사항 변경은 CCB 승인을 거쳐야만 반영 |
| WBS/범위 기준선(Baseline) 관리 | 기준선 대비 변경 영향(일정·비용) 분석 후 승인 |
| 이해관계자 기대치 관리 | 정기 보고와 커뮤니케이션으로 사전 기대 조율 |

2) Gold Plating 대응방법

| 대응 방안 | 내용 |
|---------|------|
| 요구사항 추적표(RTM) 관리 | 요구사항과 산출물을 1:1 매핑하여 불필요 기능 식별 |
| 코드/설계 리뷰 강화 | 팀 내 리뷰 단계에서 범위 외 기능 여부 점검 |
| MVP/애자일 원칙 내재화 | "필요한 만큼만" 개발하는 조직 문화 조성 |
| PM의 명확한 범위 커뮤니케이션 | 개발팀에게 범위기술서와 인수기준을 명확히 공유 |

```
[통합 대응 프레임워크]

           범위기준선(Scope Baseline) 확정
                    │
      ┌─────────────┴─────────────┐
      ▼                           ▼
고객발 요구 변경                개발자발 기능 추가
      │                           │
  CCB 공식 승인 절차           RTM 기반 범위 외 여부 점검
      │                           │
      └───────────► 범위기준선 갱신 또는 반려 ◄───────┘
```

- Scope Creep은 외부 요구 변경에 대한 통제(CCB)로, Gold Plating은 내부 개발자의 자율적 추가에 대한 점검(RTM)으로 대응해야 두 유형의 범위 이탈을 모두 방지할 수 있다.  "끝"

### 실무 제언

**"작은 부탁"이 누적되는 현장의 함정**
- **챌린지**: 고객의 사소해 보이는 요청("이 버튼 하나만 추가해주세요")을 매번 정식 변경 절차 없이 수용하다 보면, 누적되어 프로젝트 막바지에는 감당할 수 없는 범위 초과 상태가 된다.
- **제언**: 아무리 작은 요청이라도 반드시 변경요청서(CR)를 작성하게 하는 '무예외 원칙'을 계약서에 명시하고, 소규모 변경은 약식 승인 절차(Fast-track CCB)로 신속 처리하되 반드시 기록을 남겨야 한다.

**개발자의 선의가 만드는 리스크**
- **챌린지**: 우수한 개발자일수록 "이왕이면 더 좋게"라는 선의로 요구되지 않은 기능을 추가하지만, 이는 테스트 범위 누락, 일정 지연, 유지보수 부담 증가로 이어진다.
- **제언**: 개발 착수 전 요구사항 추적표(RTM)를 팀 전체에 공유하여 "정의된 범위 내 완성도"를 목표로 삼는 품질 문화를 조성하고, 추가 아이디어는 백로그에 별도 등록해 차기 스프린트에서 정식 검토하도록 유도한다.

**애자일 환경에서의 범위 통제 재해석**
- **챌린지**: 애자일 방법론은 변화 수용을 미덕으로 여기기 때문에, Scope Creep과 정상적인 백로그 우선순위 조정을 구분하기 어렵다는 오해가 있다.
- **제언**: 스프린트 내에서는 범위 고정(Scope Freeze) 원칙을 유지하고, 변경은 반드시 다음 스프린트 계획 단계에서 Product Owner의 백로그 재우선순위화를 통해 공식적으로 반영하는 것으로 스프린트 단위의 범위 통제를 확립해야 한다.
