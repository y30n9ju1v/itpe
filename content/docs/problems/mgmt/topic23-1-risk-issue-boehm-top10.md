## 해설

### 출제 배경 및 의도

현장의 PM들은 "위험(Risk)"과 "이슈(Issue)"라는 용어를 혼용하는 경우가 많으나, 이 둘은 관리 시점과 대응 방식이 근본적으로 다르다. 위험은 아직 발생하지 않은 불확실한 미래 사건이고, 이슈는 이미 발생하여 즉각적 조치가 필요한 현재 문제다. 이 구분을 명확히 하지 못하면 위험관리 프로세스가 사후약방문식 이슈 대응으로 전락하게 된다.

이 문제는 개념 비교(가)에 그치지 않고, Barry Boehm이 1991년 제시한 소프트웨어 프로젝트의 10대 위험 목록(나)을 통해 실제로 어떤 위험이 반복적으로 발생하는지 구체적으로 열거하도록 요구하며, 나아가 위험과 이슈를 하나의 프로세스로 통합 관리하는 실무 체계(다)까지 묻는다. 채점위원은 Boehm의 리스트를 단순 암기가 아니라 현대 IT 프로젝트(클라우드, 애자일)에 재해석하여 설명할 수 있는지를 고득점 포인트로 본다.

### 1. 위험관리 vs 이슈관리 비교

정 의  • 위험(Risk)을 "발생 여부가 불확실하나 발생 시 프로젝트 목표에 긍정적 또는 부정적 영향을 미치는 사건"으로, 이슈(Issue)를 "이미 발생하여 현재 프로젝트에 영향을 미치고 있는 확정된 문제"로 정의한다(PMBOK).

```
[위험과 이슈의 시간축 관계]

시간 흐름 ──────────────────────────────────────▶

[식별된 위험] ──(발생 확률 X%)──▶ [위험 현실화] ──▶ [이슈로 전환]
     │                                                    │
     ▼                                                    ▼
사전 대응(Proactive)                              사후 대응(Reactive)
- 회피/전가/완화/수용                              - 이슈 로그 등록
- Risk Register 관리                               - 즉시 해결 담당자 지정
- 확률×영향 정량 평가                              - 에스컬레이션 절차
```

| 구분 | 위험관리(Risk Management) | 이슈관리(Issue Management) |
|------|--------------------------|---------------------------|
| 대상 | 발생 여부가 불확실한 미래 사건 | 이미 발생이 확정된 현재 문제 |
| 관리 시점 | 사전(Proactive) | 사후(Reactive) |
| 접근 방식 | 확률(Probability) × 영향(Impact) 정량 평가 | 즉시 조치 및 해결 담당자 배정 |
| 관리 도구 | Risk Register, Risk Breakdown Structure | Issue Log, 에스컬레이션 매트릭스 |
| 대응 전략 | 회피/전가/완화/수용(4대 전략) | 근본원인분석(RCA), 즉시 시정조치 |
| 목표 | 발생 확률과 영향 자체를 낮춤 | 이미 발생한 영향을 최소화·해결 |

- 실무에서는 위험이 현실화되는 순간 Risk Register에서 Issue Log로 전환 등록하는 트리거 프로세스를 운영하여 두 관리 체계의 연속성을 확보한다.

### 2. Boehm의 10대 위험 목록

정 의  • Barry Boehm이 「Software Risk Management」(1991)에서 다수의 소프트웨어 프로젝트 사례를 분석하여 도출한, 프로젝트 실패에 가장 빈번하게 기여하는 10가지 위험 요소이다.

| 순위 | 위험 요소 | 현대적 재해석(클라우드/애자일 환경) |
|------|----------|-----------------------------------|
| 1 | 인력 부족(Personnel Shortfalls) | 클라우드/AI 전문 인력 확보 경쟁 심화 |
| 2 | 비현실적 일정·예산(Unrealistic Schedules and Budgets) | 애자일 스프린트 과소 산정, 벨로시티 과신 |
| 3 | 잘못된 기능 개발(Developing the Wrong Software Functions) | 요구사항 불명확 상태의 조기 착수(MVP 오남용) |
| 4 | 잘못된 사용자 인터페이스 개발(Developing the Wrong UI) | 사용자 검증 없는 UI 확정 |
| 5 | 도금(Gold Plating) | 불필요한 마이크로서비스 과설계 |
| 6 | 요구사항의 지속적 변경(Continuing Stream of Requirements Changes) | 애자일에서 스코프 크립(Scope Creep) 만연 |
| 7 | 외부 공급 컴포넌트 결함(Shortfalls in Externally Furnished Components) | 오픈소스/서드파티 API·SaaS 의존성 리스크 |
| 8 | 외부 수행 작업 결함(Shortfalls in Externally Performed Tasks) | 멀티 벤더 아웃소싱 협업 실패 |
| 9 | 실시간 성능 문제(Real-time Performance Shortfalls) | 클라우드 오토스케일링 미비로 인한 지연 |
| 10 | 컴퓨터과학의 한계 도전(Straining Computer Science Capabilities) | 생성형 AI 등 미검증 신기술 무리한 적용 |

```
[Boehm 10대 위험의 프로젝트 단계별 분포]

기획 단계     ┃ 2.비현실적 일정  3.잘못된 기능  6.요구사항 변경
설계 단계     ┃ 4.잘못된 UI  5.도금(Gold Plating)  10.신기술 과신
구현 단계     ┃ 1.인력 부족  7.외부 컴포넌트 결함  9.실시간 성능
전 단계 공통  ┃ 8.외부 수행 작업 결함
```

### 3. 위험과 이슈의 통합관리 방안

```
[통합 관리 프로세스: Risk-Issue 연계 워크플로우]

① 위험 식별 (Risk Identification)
   └─ Boehm 10대 위험 체크리스트 + 브레인스토밍/체크리스트법
           │
           ▼
② 위험 분석(정성/정량) → Risk Register 등재
   └─ 확률×영향 매트릭스로 우선순위화(P-I Matrix)
           │
           ▼
③ 위험 대응 계획 수립(회피/전가/완화/수용)
   └─ 트리거 조건(Trigger Condition) 사전 정의
           │
           ▼
④ 위험 모니터링 ──[트리거 조건 충족?]──Yes──▶ ⑤ 이슈로 전환 등록(Issue Log)
   └─ 조건 미충족 시 지속 모니터링              └─ 담당자·기한 즉시 지정
                                                          │
                                                          ▼
                                                 ⑥ 이슈 해결 및 교훈(Lessons Learned) 반영
                                                    → Risk Register 갱신(유사 위험 재평가)
```

| 통합관리 요소 | 내용 |
|--------------|------|
| 단일 등록부(Unified Register) | Risk Register와 Issue Log를 하나의 시스템(예: Jira)에서 연계 관리, 위험 ID와 이슈 ID를 상호 참조 |
| 트리거 기반 자동 전환 | 위험의 조기 경보 지표(Leading Indicator)가 임계치를 넘으면 자동으로 이슈로 승격 알림 |
| 정기 검토 회의 | 주간 위험/이슈 통합 검토 회의(Risk & Issue Review)에서 양쪽을 함께 다룸 |
| 교훈 관리(Lessons Learned) | 해결된 이슈는 조직 위험 데이터베이스(RBS)에 반영하여 향후 유사 프로젝트의 위험 식별 정확도 향상 |

- 위험관리와 이슈관리를 단일 등록부와 트리거 기반 전환 체계로 통합함으로써, 위험 예방과 이슈 대응이 단절되지 않는 연속적 관리 체계를 구축할 수 있다.  "끝"

### 실무 제언

**위험과 이슈의 경계 모호로 인한 관리 공백**
- **챌린지**: 실무에서는 위험이 서서히 현실화되는 경우가 많아 "아직 위험인지, 이미 이슈인지" 판단이 애매해지고, 이 공백 기간에 대응이 지연되는 경우가 빈번하다.
- **제언**: 위험별로 명확한 트리거 조건(예: "SPI가 0.9 미만으로 2주 연속 지속되면 이슈로 전환")을 사전에 정의하여 판단의 주관성을 제거하고 대응 지연을 방지한다.

**Boehm 목록의 현대적 재적용**
- **챌린지**: 1991년 제시된 Boehm의 목록은 폭포수 모델 시대 기준이라 클라우드·애자일·생성형 AI가 보편화된 현재 환경에 그대로 적용하기 어렵다는 지적이 있다.
- **제언**: 조직 내 과거 프로젝트 사후 분석(Retrospective) 데이터를 축적하여 Boehm의 10대 위험을 조직 특화 위험 체크리스트로 재구성하고, 정기적으로(연 1회 이상) 갱신하여 실효성을 유지한다.

**멀티 벤더 환경에서의 이슈 에스컬레이션 지연**
- **챌린지**: 외부 수행 작업(Boehm 8번)에서 발생한 이슈는 벤더 간 책임 소재 다툼으로 에스컬레이션이 지연되는 경우가 많다.
- **제언**: 계약 단계에서부터 벤더별 이슈 대응 SLA(예: 24시간 내 1차 응답)와 에스컬레이션 매트릭스를 명문화하고, PMO가 벤더 간 이슈를 조정하는 단일 창구 역할을 수행하도록 한다.
