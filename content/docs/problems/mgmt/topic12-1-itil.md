## 해설

### 출제 배경 및 의도

ITIL은 2019년 V4로 개정되면서 기존의 선형적 서비스 수명주기 모델에서 벗어나, 애자일·데브옵스·린(Lean) 사고를 반영한 유연한 서비스 가치 시스템(SVS)으로 진화했다. 이는 클라우드 네이티브, 마이크로서비스, 지속적 배포(CI/CD) 환경에서 전통적 ITIL V3의 순차적 프로세스가 더 이상 실무에 맞지 않는다는 문제의식에서 출발한다.

이 문제는 V4의 새로운 구성요소(가), V3 대비 변화(나)를 통해 최신 ITSM 표준의 이해도를 확인하고, 나아가 계약관리 관점에서 아웃소싱 SoW(Statement of Work) 유형까지 연결지어 묻는다. 이는 IT경영 과목이 기술적 프레임워크뿐 아니라 계약·조달 실무까지 통합적으로 다룬다는 것을 보여준다.

### 1. ITIL V4의 구성요소

정 의 • ITIL V4를 조직이 이해관계자와 함께 가치를 공동창출(Co-creation)하도록, 서비스 가치 사슬·4대 차원·가이딩 원칙·실무(Practice)로 구성된 서비스 가치 시스템(SVS) 기반 ITSM 프레임워크라 한다.

```
[ITIL V4 서비스 가치 시스템(SVS: Service Value System)]
     ┌─────────── 거버넌스(Governance) ───────────┐
     │                                              │
  기회/수요 →[서비스 가치 사슬(SVC)]→ 가치(Value)   │
     │        ┌─Plan─Improve─Engage─┐              │
     │        │Design&Transition    │              │
     │        │Obtain/Build─Deliver&Support│        │
     │        └─────────────────────┘              │
     │   ↑ 34개 ITIL 실무(Practices) 지원            │
     │   ↑ 7 Guiding Principles가 전체를 관통         │
     └──────────────────────────────────────────────┘
```

| 구성요소 | 내용 |
|------|------|
| 서비스 가치 사슬(SVC) | Plan, Improve, Engage, Design&Transition, Obtain/Build, Deliver&Support 6개 활동 |
| 4대 차원(4 Dimensions) | 조직/인력, 정보/기술, 파트너/공급자, 가치흐름/프로세스 |
| 7대 가이딩 원칙 | 가치에 집중, 현재 위치에서 출발, 반복적 진행/피드백 활용, 협력·가시성 증진, 전체적으로 사고, 단순화·실용화, 최적화·자동화 |
| 34개 실무(Practice) | 일반관리(14) + 서비스관리(17) + 기술관리(3) 실무 영역 |
| 지속적 개선(CI) | 모든 요소를 관통하는 개선 활동 |

### 2. ITIL V4와 ITIL V3 비교

| 구분 | ITIL V3 | ITIL V4 |
|------|---------|---------|
| 구조 | 서비스 수명주기(전략-설계-전환-운영-개선) 5단계 | 서비스 가치 사슬(SVC) 6개 활동의 유연한 조합 |
| 접근방식 | 선형적, 순차적 프로세스 중심 | 애자일/데브옵스 반영, 반복·비선형적 가치흐름 |
| 프로세스/실무 | 26개 프로세스 | 34개 실무(Practice)로 확장·재편 |
| 관점 | IT 서비스 관리 중심 | 조직 전체의 가치 공동창출(Co-creation) 중심 |
| 외부 연계 | 상대적으로 폐쇄적(IT 부서 중심) | 비즈니스, 파트너/공급자까지 포함한 개방적 생태계 |
| 문화 반영 | 전통적 폭포수식 IT 운영 문화 | 린(Lean), 애자일, 데브옵스 문화 통합 |

```
[V3 → V4 패러다임 전환]
V3: 전략→설계→전환→운영→개선 (직선형 파이프라인)
V4: Engage ⇄ Plan ⇄ Design&Transition ⇄ Obtain/Build ⇄ Deliver&Support ⇄ Improve
    (양방향 순환형 가치사슬, 어느 활동에서든 진입 가능)
```

### 3. ITSM 개념도 및 SoW 유형(PMBOK 6판 기준)

1) ITSM 개념도

```
[비즈니스 요구] → [ITSM 프로세스] → [IT서비스 제공] → [고객 가치]
                       ↑
              (ITIL 실무를 활용한 프로세스 운영)
                       ↓
              [SLA/OLA 기반 성과 측정 및 개선]
```

2) SoW(Statement of Work) 유형 - PMBOK 6판 기준

| SoW 유형 | 정의 | 적용 상황 |
|------|------|---------|
| 성과 기반 SoW(Performance-based SoW) | 달성해야 할 성과·결과(Outcome) 중심으로 요구사항 기술 | 목표는 명확하나 수행방법은 수행사 재량인 경우 |
| 기능 기반 SoW(Functional SoW) | 수행해야 할 기능·목적 중심으로 요구사항 기술 | 특정 기능 구현이 목표인 경우 |
| (참고) 상세 SoW(Design/Detailed SoW) | 무엇을, 어떻게 수행할지 구체적 절차까지 명시 | 발주기관이 방법론까지 통제하려는 경우 |

- 성과 기반 SoW는 결과 지표(SLA) 달성 여부로 계약 이행을 평가하는 반면, 기능 기반 SoW는 산출물의 기능 구현 여부로 평가한다는 점에서 ITSM의 SLA 체계와 밀접히 연동된다.  "끝"

### 실무 제언

**ITIL V4 도입 시 조직 전환 저항**
- **챌린지**: 오랫동안 ITIL V3의 프로세스 중심 사고에 익숙한 조직은 V4의 유연한 가치사슬 개념을 실무에 적용하는 데 혼란을 겪는다.
- **제언**: 전면 전환보다 기존 V3 프로세스를 V4의 실무(Practice)로 매핑하는 단계적 전환 로드맵을 수립하고, 우선 인시던트/변경관리 등 핵심 실무부터 애자일 방식으로 재설계해야 한다.

**SoW 유형 선택과 리스크 배분의 불일치**
- **챌린지**: 발주기관이 상세 SoW로 계약하면서도 성과 미달 시 수행사에게 책임을 전가하려는 경우, 계약 리스크 배분이 왜곡된다.
- **제언**: 수행 방법을 발주기관이 통제하는 상세 SoW라면 리스크는 발주기관이 더 많이 부담하고, 성과 기반 SoW는 결과 미달 시 수행사 책임을 명확히 하는 등 SoW 유형과 리스크 배분 원칙을 계약서에 일치시켜야 한다.

**34개 실무의 과도한 세분화로 인한 실행력 저하**
- **챌린지**: ITIL V4의 34개 실무를 모두 도입하려다 조직 역량 대비 과부하가 발생한다.
- **제언**: 조직의 서비스 성숙도와 비즈니스 우선순위에 따라 핵심 실무(인시던트, 변경, 문제, 서비스데스크 등) 중심으로 우선 적용하고, 나머지는 성숙도에 따라 단계적으로 확장해야 한다.
