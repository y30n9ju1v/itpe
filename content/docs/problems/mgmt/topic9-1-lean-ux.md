## 해설

### 출제 배경 및 의도

디지털 트랜스포메이션이 가속화되면서 기업은 완성된 산출물을 오래 걸려 만드는 대신, 가설을 빠르게 검증하며 고객 경험을 개선하는 방식으로 전환하고 있다. Lean UX는 Lean Startup의 "만들기-측정-학습(Build-Measure-Learn)" 사이클과 애자일의 반복 개발을 UX 설계에 접목한 방법론으로, 문서 중심의 전통적 UX 설계가 갖는 느린 피드백 주기의 한계를 극복하기 위해 등장했다.

출제자는 단순히 화면 설계 기법을 묻는 것이 아니라, 조직이 어떻게 가설 기반 사고로 전환하고 협업 방식을 바꾸는지, 그리고 그 실행 프로세스가 무엇인지를 종합적으로 검증하고자 한다. 특히 서비스 경험(UX)이 곧 매출과 직결되는 커머스·핀테크·플랫폼 산업에서 Lean UX는 실무적으로 매우 중요한 화두다.

### 1. Lean UX의 개념과 특징

정 의 • Lean UX는 산출물(Deliverable)이 아닌 결과(Outcome)에 집중하여, 최소기능제품(MVP) 수준의 프로토타입을 빠르게 만들고 실사용자 피드백을 통해 가설을 검증·개선해 나가는 협업적 UX 설계 방법론

```
[전통적 UX 대비 Lean UX 특징]
전통 UX: 요구사항 → 완벽한 와이어프레임/명세서 → 개발 → 출시 (긴 주기)
Lean UX: 가설 수립 → MVP/Prototype → 사용자 검증 → 학습 → 재설계 (짧은 반복)
```

| 특징 | 설명 |
|------|------|
| 가설 기반 | "우리는 ~라고 믿는다"는 가설을 세우고 이를 검증 |
| 협업 중심 | 디자이너·개발자·기획자가 문서 대신 화이트보드로 상시 협업 |
| 결과 지향 | 산출물(문서) 완성이 아닌 비즈니스 결과(전환율 등) 지향 |
| 빠른 반복 | 짧은 주기의 Build-Measure-Learn 순환 |
| 최소 문서화 | Just Enough Documentation, 과잉 스펙 지양 |

### 2. Lean UX의 3가지 주요 원칙

| 원칙 | 내용 | 실행 방식 |
|------|------|---------|
| ① 디자인 씽킹(Design Thinking) | 사용자 공감을 바탕으로 문제를 재정의 | 공감(Empathize)→정의→아이데이션→프로토타입→테스트 |
| ② 애자일과의 결합(Agile Collaboration) | 짧은 스프린트 단위 반복 개발과 UX 설계 병행 | 스프린트마다 UX 산출물을 점증적으로 검증 |
| ③ 린 스타트업 사고(Lean Thinking) | 가설-실험-학습의 과학적 접근으로 낭비 제거 | MVP로 최소 투자, 빠른 실패, 빠른 학습 |

```
     디자인 씽킹 ─┐
                 ├─→  Lean UX  ←── 애자일 협업
     린스타트업 ─┘
   (가설 검증)      (짧은 반복 주기)   (팀 간 지속 협업)
```

- 세 원칙은 상호 보완적으로 작동하며, "가설을 세우고(Lean) 사용자를 공감하며(Design Thinking) 짧은 주기로 검증(Agile)"하는 통합 사이클을 형성한다.

### 3. Lean UX 적용 프로세스

```
[Lean UX 프로세스: Build - Measure - Learn]

① 가설 선언(Assumption)
   └─ "우리는 [사용자]가 [기능]을 사용하면 [결과]가 나올 것이라 믿는다"
           │
           ▼
② MVP 설계 및 프로토타입 제작(Build)
   └─ 종이 프로토타입, 클릭형 프로토타입, Feature Flag 활용 최소 구현
           │
           ▼
③ 사용자 실험 및 측정(Measure)
   └─ A/B 테스트, 사용성 테스트, 클릭스트림/이벤트 로그 분석
           │
           ▼
④ 학습 및 피드백 반영(Learn)
   └─ 검증된 가설은 채택, 기각된 가설은 폐기 후 재설계
           │
           ▼
⑤ 반복(Iterate) → ①로 회귀, 스프린트 단위 지속 개선
```

| 단계 | 산출물 | 핵심 도구 |
|------|--------|---------|
| 가설 | 가설 선언문, Persona | Lean Canvas |
| Build | Wireframe, Prototype | Figma, InVision |
| Measure | 실험 결과 데이터 | Google Analytics, A/B Test 툴 |
| Learn | 검증/기각 판단 | Retrospective, 사용자 인터뷰 |

- Build-Measure-Learn 사이클을 스프린트 단위로 반복하여 가설 검증 속도와 UX 품질을 동시에 높인다.  "끝"

### 실무 제언

**과도한 MVP 단순화로 인한 사용자 경험 훼손**
- **챌린지**: MVP를 지나치게 최소화하면 핵심 가치 검증에는 유리하지만 초기 사용자 이탈률이 높아지고 브랜드 신뢰도가 저하될 위험이 있다.
- **제언**: "최소 매력적 제품(Minimum Lovable Product)" 개념을 병행 적용하여, 기능은 최소화하되 사용자가 실제로 만족할 수 있는 최소한의 완성도는 확보해야 한다.

**정성적 가설 검증의 한계**
- **챌린지**: 소규모 사용자 인터뷰만으로 가설을 검증할 경우 확증 편향(Confirmation Bias)에 빠질 위험이 크다.
- **제언**: 정성적 사용성 테스트와 정량적 A/B 테스트 데이터를 함께 활용하는 Mixed-Method 검증 체계를 구축하고, 통계적 유의성을 갖춘 표본 크기를 확보해야 한다.

**조직 문화 전환의 어려움**
- **챌린지**: Lean UX는 문서보다 협업과 실험을 우선시하므로, 규제 산업(금융, 공공)처럼 사전 문서화가 필수인 조직에서는 도입 저항이 크다.
- **제언**: 규제 준수가 필요한 문서(요구정의서 등)는 최소 수준으로 병행 유지하면서, UX 설계와 검증 과정에만 Lean 방식을 적용하는 하이브리드 거버넌스를 설계해야 한다.
