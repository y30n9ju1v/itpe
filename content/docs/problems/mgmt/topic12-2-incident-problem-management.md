ITSM 의 인시던트 관리와 문제 관리에 대해서 설명하고, ITIL v3 를 Service Lifecycle 중심으로 설명하시오.

## 해설

### 출제 배경 및 의도

12-1이 ITIL V4와 SoW 계약 관점을 다뤘다면, 이 문제는 ITIL V3의 근간인 서비스 수명주기(Service Lifecycle)와 그 안의 대표적 운영 프로세스인 인시던트 관리·문제 관리에 초점을 맞춘다. 인시던트 관리와 문제 관리는 실무에서 가장 빈번히 혼동되는 개념으로, "장애가 발생했을 때 빨리 복구하는 것"과 "장애의 근본원인을 찾아 재발을 방지하는 것"의 차이를 명확히 구분하는지가 핵심 채점 포인트다.

또한 ITIL V3의 5단계 수명주기 구조를 정확히 설명함으로써, V4로 개정되기 이전의 전통적 ITSM 표준에 대한 기본기를 갖췄는지도 함께 검증한다.

### 1. 인시던트 관리 vs 문제 관리 개념 비교

정 의 • 인시던트 관리(Incident Management)는 서비스 중단·품질 저하를 신속히 정상 상태로 복구하는 것이 목적이며, 문제 관리(Problem Management)는 인시던트의 근본원인(Root Cause)을 규명하여 재발을 방지하는 것이 목적인 ITSM 운영 프로세스

| 구분 | 인시던트 관리 | 문제 관리 |
|------|------|---------|
| 목적 | 서비스 신속 복구(임시조치 포함) | 근본원인 제거(영구조치) |
| 시간 관점 | 단기(Reactive, 즉각 대응) | 중장기(Proactive, 예방 중심) |
| 산출물 | 인시던트 티켓, 임시 해결책(Workaround) | 알려진 오류(Known Error), 영구 해결책 |
| 핵심 지표 | MTTR(평균 복구시간) | 재발 건수, 근본원인 제거율 |
| 연계 관계 | 반복 인시던트 발생 시 문제로 전환(에스컬레이션) | 문제 해결 후 변경관리(Change)로 영구조치 반영 |

```
[인시던트-문제-변경 프로세스 흐름]
① 인시던트 발생 → 서비스데스크 접수 → 1차 분류/우선순위 부여
② 임시조치(Workaround)로 신속 복구 → 인시던트 종료
③ 동일/유사 인시던트 반복 → 문제로 전환(Problem Record 생성)
④ 근본원인분석(RCA) → 알려진 오류(Known Error) 등록
⑤ 영구 해결책 도출 → 변경관리(Change Management) 요청
⑥ 변경 적용 → 문제 종료 → 재발 방지 확인
```

- 인시던트 관리가 "불을 끄는 것"이라면, 문제 관리는 "불이 왜 났는지 조사해 재발을 막는 것"이다.

### 2. 인시던트 관리와 문제 관리 프로세스 상세

1) 인시던트 관리 프로세스

| 단계 | 활동 |
|------|------|
| 접수/기록 | 서비스데스크를 통한 인시던트 접수, 티켓 생성 |
| 분류/우선순위 | 영향도×긴급도 매트릭스로 우선순위 결정 |
| 조사/진단 | 1차/2차/3차 지원(Tier) 단계별 에스컬레이션 |
| 해결/복구 | Workaround 적용, 서비스 정상화 |
| 종료 | 사용자 확인 후 티켓 종료 |

2) 문제 관리 프로세스

| 단계 | 활동 |
|------|------|
| 문제 식별 | 반복 인시던트 패턴 분석, 사전 예방적 문제 탐지 |
| 근본원인분석(RCA) | 5-Why, 어골도(Fishbone) 등 기법 활용 |
| 알려진 오류 등록 | Known Error Database(KEDB) 관리 |
| 해결책 수립 | 영구 조치안 도출, 변경관리 요청(RFC) |
| 검토/종료 | 재발 여부 모니터링 후 문제 종료 |

### 3. ITIL v3 Service Lifecycle

```
[ITIL V3 서비스 수명주기 5단계]
        ┌────────── 지속적 서비스 개선(CSI) ──────────┐
        │                                              │
서비스전략(SS) → 서비스설계(SD) → 서비스전환(ST) → 서비스운영(SO)
   전략수립          SLA/가용성            테스트/배포        인시던트/문제
   포트폴리오         용량/보안 설계        릴리즈관리          이벤트/요청관리
        │                                              │
        └──────────────────────────────────────────────┘
```

| 단계 | 핵심 프로세스 |
|------|------|
| 서비스 전략(Service Strategy) | 서비스 포트폴리오 관리, 수요관리, 재무관리 |
| 서비스 설계(Service Design) | SLA 관리, 가용성/용량/IT서비스연속성/정보보안 관리, 공급자 관리 |
| 서비스 전환(Service Transition) | 변경관리, 자산 및 구성관리(SACM), 릴리즈/배포관리, 지식관리 |
| 서비스 운영(Service Operation) | 인시던트관리, 문제관리, 이벤트관리, 요청충족, 접근관리 |
| 지속적 서비스 개선(CSI) | 7단계 개선 프로세스, KPI 기반 성과 측정·개선 |

- 인시던트 관리와 문제 관리는 "서비스 운영(Service Operation)" 단계에 속하며, 문제 해결을 위한 영구조치는 "서비스 전환" 단계의 변경관리와 연계된다.  "끝"

### 실무 제언

**인시던트와 문제의 혼동으로 인한 근본원인 방치**
- **챌린지**: 현업에서는 인시던트를 빠르게 종료하는 데만 집중해 동일 장애가 반복되어도 문제로 전환하지 않는 경우가 많다.
- **제언**: 인시던트 관리 도구에 반복 발생 임계치(예: 동일 유형 인시던트 월 3회 이상)를 설정해 자동으로 문제 레코드를 생성하는 프로세스 자동화를 도입해야 한다.

**KEDB(알려진 오류 데이터베이스) 활용 저조**
- **챌린지**: 문제 해결 후 KEDB에 축적된 지식이 다음 인시던트 대응 시 활용되지 못해 동일한 진단 과정을 반복하는 비효율이 발생한다.
- **제언**: 인시던트 접수 시점에 KEDB를 자동 검색해 유사 사례의 Workaround를 제시하는 지식관리 연계 체계(1차 지원 조직의 셀프서비스화)를 구축해야 한다.

**CSI(지속적 서비스 개선)의 형식적 운영**
- **챌린지**: 서비스 운영 단계의 인시던트·문제 데이터가 CSI 단계로 환류되지 않아 동일한 유형의 장애가 매년 반복된다.
- **제언**: 문제관리 종료 시 CSI 레지스터에 개선 과제로 등록하고, 분기별 서비스 리뷰에서 KPI(재발률, MTTR 추이) 기반으로 개선 효과를 검증하는 PDCA 환류 체계를 운영해야 한다.
