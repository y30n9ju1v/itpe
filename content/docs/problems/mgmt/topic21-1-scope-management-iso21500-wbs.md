## 문제

프로젝트 관리 국제표준인 ISO21500에는 관리 주체별로 단계별 수행 프로세스에 대하여 명시하고 있다.

- 가. ISO21500에서 범위관리를 위해 기획 단계와 통제 단계에 수행하는 세부 활동에 대하여 설명하시오.
- 나. 작업분류체계(WBS: Work Breakdown Structure)에 대하여 설명하시오. (정의, 주요투입물, 작성방법 등)
- 다. 프로젝트 수행 경험을 통해 WBS가 범위관리 외에 일정관리, 의사소통관리 등에 어떻게 활용되는지 사례를 제시하시오.

## 해설

### 출제 배경 및 의도

ISO21500은 PMBOK을 기반으로 제정된 프로젝트관리 국제표준(ISO)으로, 국가·산업에 무관하게 통용되는 프로젝트관리 공통 언어를 제공한다. 이 문제는 ISO21500의 프로세스 그룹(기획-실행-통제) 관점에서 범위관리가 구체적으로 어떤 활동으로 구성되는지, 그리고 범위관리의 핵심 산출물인 WBS가 실무에서 얼마나 다목적으로 활용되는지를 균형있게 묻고 있다.

특히 (다)항은 "프로젝트 수행 경험을 통해"라는 표현으로 실무 경험에 기반한 응용력을 요구한다. 이는 WBS를 단순히 범위관리 산출물로 국한하지 않고, 일정관리(Activity 도출)·의사소통관리(보고 체계 기준)·비용관리(원가 집계 단위)의 기준선(Baseline)으로 확장 활용하는 능력을 평가하는 응용형 문제이다. 21-2(Scope Creep/Gold Plating)가 범위의 '통제 실패' 관점이라면, 이 문제는 범위의 '구조화와 활용' 관점에 초점을 둔다.

### 1. ISO21500 개요 및 범위관리 프로세스 그룹

정 의  • ISO21500은 프로젝트관리에 대한 국제표준(2012년 제정)으로, 39개 프로세스를 5개 프로세스 그룹(착수-기획-실행-통제-종료)과 10개 주제 그룹(범위, 일정, 원가 등)으로 구조화한 프레임워크이다.

```
[ISO21500 범위관리 프로세스 흐름]

착수 → [기획] 범위 정의, WBS 개발 → [실행] → [통제] 범위 통제 → 종료
              │                                    │
        요구사항 수집                          변경통제, 형상관리
        범위기술서 작성                        범위 검증(인수)
        WBS 작성                              편차 분석
```

### 2. 가. 범위관리 기획 단계와 통제 단계 세부 활동

| 단계 | 세부 활동 | 산출물 |
|------|---------|--------|
| 기획 | 요구사항 수집(이해관계자 인터뷰, 워크숍) | 요구사항 문서 |
| 기획 | 범위 정의(프로젝트 범위기술서 작성) | 범위기술서(Scope Statement) |
| 기획 | WBS 개발(작업 단위 분할) | WBS, WBS 사전(Dictionary) |
| 통제 | 범위 검증(인수기준 대비 산출물 검토) | 인수된 인도물 |
| 통제 | 범위 통제(변경요청 처리, 형상관리 연계) | 변경통제기록, 갱신된 기준선 |

- 기획 단계가 "무엇을 만들 것인가"를 정의한다면, 통제 단계는 "정의된 대로 만들어지고 있는가"를 지속적으로 검증하는 활동이다.

### 3. 나. 작업분류체계(WBS)

정 의  • WBS는 프로젝트의 전체 범위를 인도물(Deliverable) 중심으로 계층적으로 분할하여, 관리 가능한 최소 작업 단위(Work Package)까지 세분화한 도표이다.

```
[WBS 계층 구조 예시]

Level 0: 프로젝트 전체
  Level 1: 요구분석 / 설계 / 개발 / 테스트 / 이행
    Level 2: 개발 > 화면개발 / DB개발 / 인터페이스개발
      Level 3(Work Package): 화면개발 > 로그인화면 / 마이페이지화면
```

| 항목 | 내용 |
|------|------|
| 주요 투입물 | 범위기술서, 요구사항 문서, 조직 프로세스 자산(과거 WBS 템플릿) |
| 작성 원칙 | 100% Rule(상위 작업 = 하위 작업의 합), MECE(중복·누락 없음) |
| 작성 방법 | 하향식 분해(Top-Down Decomposition), 유사 프로젝트 벤치마킹 |
| Work Package 기준 | 8/80 Rule(작업 하나가 8~80시간 내 완료 가능한 수준) |

### 4. 다. WBS의 타 관리영역 활용 사례

```
[WBS를 매개로 한 관리영역 통합]

        WBS (Work Package 단위)
       /        |         \
  일정관리    비용관리    의사소통관리
 (Activity   (원가집계   (보고체계
  도출·      코드/CBS)   기준, 담당자
  일정표)                지정)
```

| 관리영역 | WBS 활용 사례 |
|---------|-------------|
| 일정관리 | Work Package를 Activity로 분해하여 PDM 네트워크 작성, 간트차트 수립 |
| 비용관리 | WBS 코드에 원가계정을 매핑한 CBS(Cost Breakdown Structure)로 EVM 산정 |
| 의사소통관리 | WBS 단위로 담당자(RACI)를 지정하고, 주간 보고 체계를 WBS 항목별로 구성 |
| 인력관리 | Work Package 단위로 필요 역량·투입 공수를 산정해 자원 배정 |

- 실무 사례: 공공 SI 프로젝트에서 WBS의 Level 3(Work Package)를 기준으로 PM이 매주 진척률 보고 양식을 구성하고, 동일 코드 체계로 EVM(PV/EV/AC)을 산출하여 일정·비용·의사소통을 하나의 기준선으로 통합 관리한 경험이 있다.  "끝"

### 실무 제언

**WBS 세분화 수준의 딜레마**
- **챌린지**: WBS를 지나치게 세분화하면 관리 오버헤드가 커지고, 반대로 너무 크게 잡으면 진척 관리가 부정확해진다.
- **제언**: 8/80 Rule을 기준으로 하되, 고위험·고가시성 작업은 세분화 수준을 높이고 정형화된 반복 작업은 상대적으로 크게 묶는 위험 기반 차등 세분화 전략을 적용해야 한다.

**WBS와 애자일 백로그의 연계**
- **챌린지**: 하이브리드 프로젝트에서는 전통적 WBS와 애자일 제품 백로그(Product Backlog)를 별도로 관리하여 이중 관리 부담이 발생한다.
- **제언**: 상위 레벨은 WBS로 인도물 범위를 고정하고, 하위 Work Package는 스프린트 백로그 항목으로 매핑하는 계층적 연계 모델을 구축해야 한다.

**WBS 사전(Dictionary) 관리 소홀 문제**
- **챌린지**: WBS 도표만 작성하고 각 작업의 완료 기준·담당자·산출물을 명시한 WBS 사전을 소홀히 하여 실제 통제 단계에서 범위 검증 기준이 모호해지는 경우가 많다.
- **제언**: WBS 사전을 형상관리 항목으로 등록해 변경 이력을 추적하고, 각 Work Package의 인수기준(DoD: Definition of Done)을 명문화해야 한다.
