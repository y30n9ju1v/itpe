## 해설

### 출제 배경 및 의도

감리는 "언제, 무엇을" 점검할지가 개발 방법론에 따라 달라진다. 폭포수 기반의 구조적/정보공학적 개발과, 반복·점증적인 객체지향/컴포넌트기반 개발은 산출물 체계와 개발 리듬 자체가 다르기 때문에, 동일한 감리시점·영역을 기계적으로 적용하면 실효성이 떨어진다. 이에 한국지능정보사회진흥원(NIA)은 "정보시스템 감리 점검 프레임워크"를 통해 개발모델별 감리시점·영역을 표준화하여 제시하고 있다.

이 문제는 감리인이 방법론 특성을 이해하지 못한 채 획일적 체크리스트만 들이대는 문제(예: 애자일 프로젝트에 폭포수식 단계별 산출물을 요구하는 오류)를 예방하기 위한 실무 역량을 검증한다. 최근 MSA·컴포넌트 기반 개발이 공공사업에서도 확산되면서, 감리인의 방법론별 맞춤 점검 역량이 더욱 중요해지고 있다.

### 1. 감리점검 프레임워크 V3.0 개요

정 의  • NIA가 제시하는 감리점검 프레임워크는 개발모델(구조적/객체지향 등)별로 감리시점(언제 감리하는가)과 감리영역(무엇을 점검하는가)을 표준화한 지침이다.
       - 동일 SDLC 산출물이라도 개발모델에 따라 명칭·구조·검증 포인트가 달라지므로 모델별 맞춤 프레임워크가 필요하다.

```
[개발모델별 감리 프레임워크 분기]
정보시스템 개발 사업
     ├─ 구조적/정보공학적 모델 → 단계형(waterfall) 산출물 중심 감리
     └─ 객체지향/컴포넌트기반 모델 → 반복형(iterative) + 아키텍처 중심 감리
```

### 2. 가. 구조적/정보공학적 개발 모델의 감리시점과 감리영역

| 감리시점 | 대응 SDLC 단계 | 감리영역 |
|---------|-------------|---------|
| 착수감리 | 사업착수 | 사업계획서, 추진체계, WBS 적정성 |
| 요구사항분석 감리 | 요구분석 | 요구사항정의서, SIRS 완전성/일관성 |
| 설계감리 | 구조적 설계(DFD, ERD) | 데이터흐름도, 개체관계도, 프로그램명세서 |
| 구현/시험 감리 | 코딩/단위·통합시험 | 프로그램 목록, 시험계획서/결과서 |
| 종료감리 | 인수/이행 | 사용자매뉴얼, 운영이관계획서 |

```
[구조적 개발모델 감리 흐름]
요구분석(SIRS) → 설계(DFD/ERD 기반) → 구현(모듈 코딩) → 시험(단위→통합→인수)
     감리①            감리②              감리③              감리④
- 각 단계 종료 시점(Milestone)에 정합성 위주로 점검
- DFD 계층 간 일관성, ERD 정규화 수준이 핵심 점검 포인트
```

- 구조적 개발은 폭포수(Waterfall) 흐름을 따르므로, 감리시점이 SDLC 단계 경계와 명확히 일치하며 산출물 간 정합성(요구사항→설계→코드 추적성)이 핵심 감리영역이다.

### 3. 나. 객체지향/컴포넌트기반 개발 모델의 감리시점과 감리영역

| 감리시점 | 대응 개발 단계 | 감리영역 |
|---------|-------------|---------|
| 착수감리 | 사업착수 | 반복주기(Iteration) 계획, 아키텍처 비전 |
| 분석/설계 감리 | 유스케이스/클래스 설계 | 유스케이스 명세서, 클래스다이어그램, 컴포넌트 명세 |
| 반복주기별 감리 | 각 Iteration/Sprint 종료 | 반복 산출물(동작 소프트웨어), 회고 결과 |
| 통합/시험 감리 | 컴포넌트 통합 시험 | 인터페이스 명세, 컴포넌트 재사용성, API 계약(Contract) |
| 종료감리 | 인수/이행 | 컴포넌트 배포 구조, 유지보수 용이성 |

```
[객체지향/컴포넌트기반 감리 흐름]
반복1 → 반복2 → 반복3 → ... → 통합 → 인수
  │       │       │              │
  감리(반복마다) 아키텍처/컴포넌트 일관성 점검   최종 통합감리
- 폭포수처럼 1회성 단계 경계가 아니라, 반복주기마다 감리 포인트 존재
- 컴포넌트 간 인터페이스 계약, 재사용성, 결합도가 핵심 점검 포인트
```

- 객체지향/컴포넌트기반 개발은 반복·점증적(Iterative & Incremental) 특성상, 감리시점이 매 반복주기 종료 시점마다 존재할 수 있으며, 감리영역도 "산출물 정합성"보다 "아키텍처 일관성·컴포넌트 재사용성"에 무게중심이 있다.

### 4. 두 모델 비교 및 감리 접근 차별화

| 구분 | 구조적/정보공학적 모델 | 객체지향/컴포넌트기반 모델 |
|------|---------------------|------------------------|
| 개발 흐름 | 순차적(Waterfall) | 반복·점증적(Iterative) |
| 감리시점 특징 | SDLC 단계 경계에 고정 | 반복주기(Iteration)마다 유동적 |
| 핵심 산출물 | DFD, ERD, 프로그램명세서 | 유스케이스, 클래스다이어그램, 컴포넌트명세 |
| 감리영역 무게중심 | 산출물 간 정합성/추적성 | 아키텍처 일관성/인터페이스 계약 |
| 리스크 포인트 | 후행 단계에서 요구사항 누락 발견 | 반복 간 아키텍처 표류(Architecture Drift) |

- 개발 모델의 특성에 따라 감리시점과 감리영역을 차별화해야 하며, 구조적 모델은 단계 경계의 산출물 정합성을, 객체지향/컴포넌트기반 모델은 반복주기별 아키텍처 일관성을 중점 점검해야 한다.  "끝"

### 실무 제언

**애자일·반복형 개발에 폭포수식 감리를 적용하는 오류**
- **챌린지**: 감리인이 구조적 개발 산출물 체크리스트를 그대로 객체지향/반복형 프로젝트에 적용하면, 실제로는 존재하지 않는 산출물(예: 완결된 ERD)을 요구하며 불필요한 지적사항을 양산한다.
- **제언**: 착수감리 시점에 개발방법론을 명확히 확인하고, 프레임워크 V3.0의 모델별 점검항목표를 기준으로 감리 체크리스트를 사전 커스터마이징해야 한다.

**컴포넌트 재사용성 점검의 실효성 확보**
- **챌린지**: 컴포넌트 기반 개발에서 재사용성은 문서상 주장에 그치고 실제로는 프로젝트별 재개발이 반복되는 경우가 많다.
- **제언**: 감리영역에 "컴포넌트 재사용 이력 관리대장"을 포함시켜, 실제 재사용 실적과 API 계약 준수 여부를 정량적으로 검증해야 한다.

**반복형 개발의 감리 타이밍 설계**
- **챌린지**: 반복주기마다 감리를 수행하면 감리 비용·기간이 과도하게 증가하고, 반대로 종료 시점에만 감리하면 아키텍처 표류를 뒤늦게 발견한다.
- **제언**: 주요 마일스톤이 되는 반복주기(예: 3~4회차마다)에 선별적으로 경량 감리(아키텍처 정합성 위주)를 배치하는 하이브리드 감리시점 설계를 적용해야 한다.
