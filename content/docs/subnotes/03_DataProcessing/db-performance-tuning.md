# 데이터베이스 튜닝 서브노트

> **두음 머리에 박기 🧠**
> - **보·이·평** (DB 튜닝 3단계: **보**색(조사) ➔ **이**행(설계·적용) ➔ **평**가(효과검증))
> - **설·A·S·S** (튜닝 4계층 우선순위: **설**계 ➔ **A**pplication ➔ **S**erver ➔ **S**ystem)

---

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **데이터베이스 튜닝(DB Tuning)** |
| **정의** | DB 성능 병목(Bottleneck)을 체계적으로 진단·제거하여 최소 비용으로 최대 성능을 달성하는 최적화 활동으로, 보색(조사)→이행(적용)→평가(검증)의 3단계 방법론과 설계→Application→Server→System 4계층의 우선순위 절차로 수행 |
| **키워드** | 슬로우 쿼리, 대기 이벤트, 실행 계획(EXPLAIN), 설계/Application/Server/System 튜닝, 반정규화 |
| **개념도** | `[성능 문제 감지: SLA 위반, 슬로우 쿼리]`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▼`<br>`[① 보색: 병목 식별·원인분석]` ➔ `[② 이행: 튜닝 방안 설계·적용]` ➔ `[③ 평가: 효과 측정·검증(반복)]`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▼ (튜닝 4계층, 우선순위 순)`<br>`[1.설계: 효과 최대·재작업 큼] → [2.Application: SQL·인덱스] → [3.Server: DBMS 파라미터] → [4.System: H/W·OS·네트워크]` |
| **구성요소** | 1. **보색(조사) 단계**: 슬로우 쿼리 분석(Slow Query Log, AWR, ASH), 대기 이벤트 분석(V$SESSION_WAIT, pg_stat_activity), 실행 계획 확인(EXPLAIN PLAN/ANALYZE), 자원 사용률(CPU·I/O·메모리·네트워크) 진단<br>2. **이행(적용) 단계**: 설계 튜닝(정규화/반정규화 조정, 인덱스 재설계), Application 튜닝(SQL 재작성-EXISTS→JOIN 변환, 바인드 변수, 페이징/배치), Server 튜닝(버퍼풀·SGA/PGA 등 메모리 파라미터, 체크포인트 빈도), System 튜닝(HDD→SSD 교체, OS 파라미터·I/O 스케줄러)<br>3. **평가 단계**: 튜닝 전후 성능 지표(응답시간, TPS, 대기시간) 비교 및 재적용 반복<br>4. **튜닝 4계층 우선순위**: 설계(효과 최대이나 재작업 비용 큼) → Application(SQL·인덱스 최적화) → Server(DBMS 파라미터 조정) → System(H/W·OS·네트워크, 최후 수단) |
| **비교** | **설계/Application 튜닝**<br>- 근본적 구조 개선(정규화 수준, SQL 로직, 인덱스)<br>- 효과 크나 개발·검증 비용과 재작업 리스크 높음<br><br>**Server/System 튜닝**<br>- 파라미터·하드웨어 조정으로 즉시 적용 가능<br>- 근본 원인 미해결 시 효과 제한적, 서버 증설은 최후 수단 |
| **차별화** | **체계적 DB 튜닝 거버넌스 전략**<br>1. **하향식 우선순위 준수**: 서버 증설(System 계층)은 설계·Application·Server 튜닝을 모두 소진한 후 최후 수단으로 적용해, 근본 원인 해결 없이 비용만 증가하는 안티패턴을 방지.<br>2. **보색 단계의 정량적 근거 확보**: AWR·ASH·EXPLAIN PLAN 등 도구 기반으로 병목의 근본 원인(Full Table Scan, Lock 대기, 비효율 조인 순서)을 정량적으로 식별한 후 이행 단계로 진입해 추측성 튜닝을 배제.<br>3. **평가-재적용 반복 사이클 고착화**: 튜닝 적용 후 성능 지표를 재측정하고 목표(SLA) 미달 시 보색 단계로 회귀하는 반복적 사이클을 운영 프로세스로 정착시켜 지속적 성능 거버넌스를 확보. |
