# 데이터 모델링: ERD, 슈퍼/서브타입, 식별자 관계 서브노트

> **두음 머리에 박기 🧠**
> - **개·속·관** (ERD 3대 구성요소: **개**체 Entity, **속**성 Attribute, **관**계 Relationship)
> - **배·포·완·부** (슈퍼/서브타입 4대 제약: 분할 제약의 **배**타적/**포**함적, 완전성 제약의 **완**전/**부**분)
> - **싱·플·개** (슈퍼/서브타입 물리 변환 3대 전략: **싱**글테이블 Single Table, **플**러스타입 Table per Type, **개**별타입 Table per Concrete Class)

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **ERD(Entity Relationship Diagram)와 관계형 데이터 모델, 슈퍼/서브타입, 식별자·비식별자 관계** |
| **정의** | 현실 세계의 업무 규칙을 개체·속성·관계로 도출하는 ERD와 이를 PK/FK 기반 테이블로 변환하는 관계형 데이터 모델링 기법으로, 공통 속성은 슈퍼타입/개별 속성은 서브타입으로 분할하는 상속 구조 설계와, 부모 PK가 자식 PK로 전이되는 식별자 관계 vs 일반 속성(FK)으로 전이되는 비식별자 관계의 선택을 포함 |
| **키워드** | ERD, 카디널리티, PK/FK 전이, 슈퍼타입/서브타입, 변별자(Discriminator), 식별자/비식별자 관계, 물리 변환 전략 |
| **개념도** | `[업무 명제]` ➔ `[ERD: 개체·속성·카디널리티 분석]` ➔ `[PK의 FK 전이]` ➔ `[관계형 모델(테이블·제약조건)]`<br>&nbsp;&nbsp;&nbsp;&nbsp;`│`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▼ (다형성 엔티티)`<br>`[슈퍼타입(공통속성)]` ── 상속 ──➔ `[서브타입1] [서브타입2] [서브타입3]` ── 물리변환(싱글/플러스/개별) ──➔ `[테이블]`<br>&nbsp;&nbsp;&nbsp;&nbsp;`│`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▼ (부모-자식 PK 전이 방식)`<br>`[식별자 관계: 실선, 부모PK→자식PK 복합키] / [비식별자 관계: 점선, 부모PK→자식 FK(일반속성)]` |
| **구성요소** | 1. **ERD 3요소(개·속·관)**: 개체(Entity)·속성(Attribute)·관계(Relationship)와 카디널리티(1:1, 1:M, M:N), 선택성(Optionality)<br>2. **관계형 모델 변환**: 개체→테이블, 속성→컬럼, 부모 PK가 자식 테이블의 FK로 전이되어 참조 무결성 형성<br>3. **슈퍼/서브타입 제약**: 분할 제약(배타적-하나의 서브타입만/포함적-복수 서브타입 겸임), 완전성 제약(완전-모든 인스턴스가 서브타입 소속/부분-미분류 인스턴스 허용)<br>4. **물리 변환 3대 전략**: Single Table(전체 통합, 조인 불필요·Null 양산), Table per Type(슈퍼+서브 분리, Null 없음·잦은 조인), Table per Concrete Class(서브타입에 공통속성 복사, 조인 없음·중복 저장)<br>5. **식별자/비식별자 관계**: 식별자 관계는 부모 PK가 자식 PK 컴포넌트로 전이(복합키, ON DELETE CASCADE, 강한 종속), 비식별자 관계는 부모 PK가 자식 일반 속성(FK)으로 전이(단일 PK 유지, SET NULL 가능, 약한 연관) |
| **비교** | **식별자 관계(Identifying)**<br>- ERD 표기: 실선, FK Not Null, 복합키 구성<br>- 극단 사용 시: 복합키 인플레이션(컬럼 5~6개 이상), 클러스터드 인덱스 집적도 저하<br><br>**비식별자 관계(Non-Identifying)**<br>- ERD 표기: 점선, FK Null 허용, 단일 PK 유지<br>- 극단 사용 시: 징검다리 조인 폭발(최상위→최하위 조회 시 전 구간 JOIN 필요), 보조 인덱스 중복 비용 |
| **차별화** | **ERD·슈퍼타입·관계 설계의 실무 적용 전략**<br>1. **도메인 성격별 관계 유형 선택**: 기준정보(부서-사원)처럼 독립적 수명주기를 갖는 도메인은 비식별자 관계로, 주문-주문상세처럼 강한 종속·이력성 정보는 식별자 관계로 설계.<br>2. **복합키 인플레이션 차단**: 식별자 관계가 3단계 이상 누적되면 대리키(Surrogate Key)를 도입해 비식별자 관계로 전환, ORM(JPA) 환경에서는 `@IdClass` 복잡도를 피하기 위해 비식별자 관계를 우선 채택.<br>3. **슈퍼/서브타입 변환 기준 수립**: 통합 조회가 빈번하면 Single Table, 서브타입별 컬럼 수·Null 비율 차이가 크면 Table per Type을 선택해 저장 공간과 조인 성능의 트레이드오프를 최적화.<br>4. **연결함정 방지와 연계**: ERD 설계 단계에서 카디널리티·선택성을 CRUD 매트릭스와 비즈니스 시나리오로 검증해 팬 트랩·캐즘 트랩(연결함정) 발생을 원천 차단. |
