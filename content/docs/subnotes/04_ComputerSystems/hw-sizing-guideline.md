# 정보시스템 하드웨어 규모산정 방법 서브노트

> **두음 머리에 박기 🧠**
> - **기·유·용** (HW 규모산정 3대 방법: **기**준 성능법 Benchmark, **유**사 시스템 기준법 Reference, **용**량 계획법 Capacity Planning)
> - **피·성·가·여** (규모산정 시 4대 고려사항: **피**크 부하, **성**장률, **가**용성 요건, **여**유율)

---

| 분류 | 기술 기술사 서브노트 작성 예시 (1교시형 포맷) |
| :--- | :--- |
| **토픽명** | **정보시스템 하드웨어 규모산정 방법 (TTAK.KO-10.0292/R3)** |
| **정의** | 공공기관 정보시스템 구축 시 CPU·메모리·스토리지 등 하드웨어 규모를 산정하기 위한 TTA 단체표준으로, **기준 성능법·유사 시스템 기준법·용량 계획법** 3가지 방법으로 적정 HW 규모를 도출 |
| **키워드** | TPC-C/SPEC CPU 벤치마크, 유사 시스템 보정 계수, 피크 부하, 여유율(30~50%), RAID 오버헤드 |
| **개념도** | `업무 분석 → 피크 부하 산정 → [ 기준 성능법 / 유사 시스템 기준법 / 용량 계획법 ] → 자원 요구량 계산 → 여유율 적용 → 최종 HW 규모`<br>`CPU 코어 수 = (최대 TPS × 평균 CPU 사용 시간) / (1 - 여유율)`<br>`스토리지 = (일 데이터 증가량 × 보존 기간) × (1 + RAID 오버헤드) × 여유율` |
| **구성요소** | 1. **기준 성능법**: TPC-C·SPEC CPU 등 표준 벤치마크 성능치를 업무 트랜잭션 환산 후 비교, 객관적이나 실제 워크로드와의 차이 존재<br>2. **유사 시스템 기준법**: 기 구축된 유사 규모·업무 시스템의 성능 데이터를 규모 차이 보정 계수로 조정해 참조, 현실적이나 적합한 참조 시스템 확보가 어려움<br>3. **용량 계획법**: 업무량(트랜잭션·사용자·데이터량) 분석 → 피크 부하 산정 → 자원 요구사항 계산 → 여유율 적용의 정량적 절차<br>4. **여유율 기준**: CPU 30~40%, 메모리 30%, 스토리지 20~30%, 고부하 시스템은 40~50% |
| **비교** | **기준 성능법 / 유사 시스템 기준법**<br>- **근거**: 표준 벤치마크치 / 기 구축 실적 데이터<br>- **장점**: 객관적 비교 가능 / 실제 운영 데이터 기반<br>- **단점**: 벤치마크와 실환경 워크로드 괴리 / 적합 참조 사례 확보 곤란<br><br>**용량 계획법**<br>- **근거**: 자체 업무량 정량 분석(피크 부하 등)<br>- **장점**: 조직 고유 요구사항 반영<br>- **단점**: 초기 데이터 부재 시 추정 오차 발생 가능 |
| **차별화** | **HA 이중화·클라우드 환경과 연계한 규모산정 실무 전략**<br>1. **HA 구성 시 자원 추가 반영**: Active-Active·Active-Standby 등 고가용성(HA) 이중화 구성 시 산정된 기본 규모에 이중화 배수를 곱해 실제 조달 규모를 산정.<br>2. **RAID 오버헤드를 포함한 스토리지 산정**: 논리적 데이터 증가량에 RAID 구성 방식(예: RAID 5의 (N-1)/N 효율)에 따른 물리적 오버헤드를 반영해야 실제 필요 디스크 용량과 일치.<br>3. **클라우드 오토스케일링과의 관계**: 온프레미스는 사전 규모산정으로 고정 자원을 확보해야 하지만, 클라우드 환경은 오토스케일링으로 피크 부하 대응 여유율을 실시간 동적 확장으로 대체할 수 있어 초기 산정 부담이 상대적으로 완화됨. |
