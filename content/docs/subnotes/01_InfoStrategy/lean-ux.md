# Lean UX의 개념과 원칙, 적용 프로세스 서브노트

> **두음 머리에 박기 🧠**
> - **디·애·린** (Lean UX 3대 원칙: **디**자인 씽킹, **애**자일 결합, **린** 스타트업 사고)
> - **가·비·측·학** (적용 프로세스 4단계: **가**설 ➔ **비**Build ➔ **측**Measure ➔ **학**Learn)

---

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **Lean UX (린 UX)** |
| **정의** | Lean UX는 산출물(Deliverable)이 아닌 결과(Outcome)에 집중하여, 최소기능제품(MVP) 수준의 프로토타입을 빠르게 만들고 실사용자 피드백을 통해 가설을 검증·개선해 나가는 협업적 UX 설계 방법론으로, Lean Startup의 Build-Measure-Learn 사이클과 애자일 반복 개발을 UX 설계에 접목한 것이다 |
| **키워드** | MVP, Build-Measure-Learn, 가설 기반 사고, Just Enough Documentation, 디자인 씽킹 |
| **개념도** | `[ 가설 선언(우리는 ~라고 믿는다) ] ➔ [ Build: Wireframe/Prototype ]`<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`▼`<br>`[ Learn: 검증/기각 판단 ] ◀── [ Measure: A/B Test·실험 데이터 ]` |
| **구성요소** | **개념·특징**: 가설 기반(우리는 ~라고 믿는다), 협업 중심(화이트보드 상시 협업), 결과 지향(전환율 등 비즈니스 결과), 빠른 반복(Build-Measure-Learn 순환), 최소 문서화(Just Enough Documentation)<br>**3대 원칙(디·애·린)**: ①디자인 씽킹 - 사용자 공감 기반 문제 재정의(Empathize→정의→아이데이션→프로토타입→테스트) ②애자일과의 결합 - 짧은 스프린트 단위 반복 개발과 UX 설계 병행 ③린 스타트업 사고 - 가설-실험-학습의 과학적 접근으로 낭비 제거(MVP로 최소 투자, 빠른 실패, 빠른 학습)<br>**적용 프로세스(가·비·측·학)**: 가설(가설선언문·Persona, Lean Canvas)→Build(Wireframe/Prototype, Figma)→Measure(실험결과 데이터, Google Analytics/A/B Test)→Learn(검증/기각 판단, Retrospective) |
| **비교** | **전통적 UX 설계**<br>- 산출물 중심: 완성된 문서·화면설계서<br>- 피드백 주기: 느림(단계별 완료 후 검토)<br><br>**Lean UX**<br>- 결과 중심: 비즈니스 성과(전환율 등)<br>- 피드백 주기: 빠름(짧은 스프린트마다 실사용자 검증) |
| **차별화** | **커머스·핀테크 등 결과 지향 산업의 Lean UX 정착 전략**<br>1. **가설 품질 관리 체계화**: "우리는 ~라고 믿는다" 가설 선언 시 반드시 측정 가능한 성공 기준(전환율 X% 등)을 명시하도록 표준 템플릿을 강제하여, 검증 불가능한 막연한 가설의 남발을 방지.<br>2. **애자일 스프린트와 UX 검증 주기의 동기화**: 개발 스프린트 종료 시점에 맞춰 UX 실험(A/B Test)의 통계적 유의성 확보 기간을 사전 설계하여, 검증되지 않은 UX 변경이 배포되는 것을 방지.<br>3. **최소 문서화 원칙의 조직적 합의**: Just Enough Documentation 원칙이 "문서화 생략"으로 오인되지 않도록, 핵심 의사결정 근거(가설·실험결과)만은 반드시 기록하는 최소 문서 기준을 조직 표준으로 명문화. |
