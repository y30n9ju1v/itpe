# 애자일 개발방법론 서브노트

> **두음 머리에 박기 🧠**
> - **개·동·고·변** (애자일 4대 가치: **개**인과 상호작용, **동**작하는 SW, **고**객 협력, **변**화 대응)
> - **계·스·일·데·회** (스크럼 5대 의식: 스프린트 **계**획, **스**프린트, **일**일 스크럼, **데**모(리뷰), **회**고)
> - **용·단·의·피·존** (XP 5대 가치: **용**기, **단**순성, **의**사소통, **피**드백, **존**중)
> - **레·그·리** (TDD 3단계 사이클: **레**드(실패 테스트 작성) → **그**린(최소 코드로 통과) → **리**팩터(코드 정제))

| **토픽명** | **애자일 개발방법론 (Agile Software Development)** |
| **정의** | 불확실성이 높은 환경에서 짧은 개발 주기(Sprint)를 반복하며 작동 가능한 소프트웨어를 신속하게 인도하고, 고객 피드백을 상시 반영하는 **고객/인간 중심 개발방법론** |
| **키워드** | 애자일 4대 선언, 스크럼(계·스·일·데·회), XP(용·단·의·피·존), 대규모 애자일(SAFe), CBD vs Agile |
| **개념도** | `[제품 백로그]` (요구사항 우선순위화)<br>&nbsp;&nbsp;&nbsp;&nbsp;`│`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▼`<br>`[스프린트 계획회의]` ➔ `[스프린트 (1~4주)]` (일일 데일리 스크럼 15분) ➔ `[잠재적 인도 가능 제품]`<br>&nbsp;&nbsp;&nbsp;&nbsp;`▲&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;│`<br>&nbsp;&nbsp;&nbsp;&nbsp;`└───────────────── [리뷰 및 회고] ──────────────────────┘` |
| **구성요소** | 1. **스크럼 3대 역할**: 제품 책임자(PO - 백로그 관리), 스크럼 마스터(SM - 장애 제거), 개발팀<br>2. **스크럼 5대 의식**: 스프린트 계획, 스프린트(수행), 일일 스크럼, 스프린트 리뷰(데모), 스프린트 회고<br>3. **XP 5대 가치**: 용기, 단순성, 의사소통, 피드백, 존중<br>4. **XP 주요 실천법**: TDD(테스트 주도), 짝 프로그래밍, 리팩토링, 공동 소유권, 지속적 통합(CI)<br>5. **TDD Red-Green-Refactor**: ①Red(실패하는 테스트 코드 선작성, 요구사항 인터페이스 명확화) → ②Green(테스트 통과용 최소 구현, 중복·지저분함 임시 허용) → ③Refactor(테스트 안전망 하에 코드 스멜 제거·가독성 향상, 회귀 결함 차단) — 테스트 코드가 살아있는 요구사항 명세서 역할<br>6. **SAFe (Scaled Agile Framework)**: Portfolio ➔ Large Solution ➔ Program ➔ Team 레벨 전사 확장 프레임워크<br>7. **애자일 장점**: 빠른 피드백, 변경 수용, 리스크 조기 발견, 팀 자율성, 고객 만족, 투명성<br>8. **애자일 단점**: 문서 부족, 범위 관리 어려움(스코프 크리프), 대규모 팀 한계, 고객 참여 필수, 장기 계획 불확실, 팀 역량 의존 |
| **비교** | **애자일 (Agile) vs 폭포수 (Waterfall)**<br>- **개발 방식**: 반복·점진적 vs 순차적(단계별)<br>- **요구사항**: 변경 허용 vs 초기 완전 정의<br>- **고객 참여**: 매 스프린트 vs 초기·최종<br>- **적합**: 빠른 변화·혁신적 제품 vs 요구사항 명확·대형 시스템<br><br>**CBD (Component Based Development) 방법론**<br>- **무게중심**: 컴포넌트 재사용 및 설계의 정밀함<br>- **접근방식**: 체계적 도메인 분석 및 설계 기반 아키텍처 우선 구축<br>- **도메인**: 안정성과 확장성이 중요한 엔터프라이즈 및 공공 대형 시스템 |
| **차별화** | **대규모 애자일(SAFe) 도입 시 계약/조직 차원의 한계 및 극복 방안**<br>1. **동적 예산제도(Lean Budgeting) 전환**: 전통적 공공/엔터프라이즈의 연간 고정 예산 구조를 탈피하여 가치 스트림(Value Stream) 단위로 분기별 예산을 유연하게 재조정하는 펀딩 모델 적용.<br>2. **LACE(Lean-Agile Center of Excellence) 조직 신설**: 기존 통제 위주의 PMO를 애자일 코칭 및 리스크 제거를 지원하는 서비스형 LACE 조직으로 개편하여 조직 저항 최소화.<br>3. **하이브리드 모델(Water-Scrum-Fall)의 현실적 적용**: 기획(법률/인허가)과 배포(인프라 검증)는 폭포수 방식을 취하되, 핵심 개발 영역에서 스크럼을 고수하여 현실적 규제 장벽 우회.<br>4. **테스트 피라미드 기반 TDD 확장**: 단위 테스트(TDD 핵심 대상)를 최하단 대량으로 두고 통합·E2E 테스트를 상단으로 갈수록 줄이는 피라미드 전략으로 대규모 프로젝트의 자동화 테스트 비용과 신뢰성을 동시에 확보. |
