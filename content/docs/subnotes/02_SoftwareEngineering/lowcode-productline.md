# 로우코드/노코드와 제품계열 방법론 서브노트

> **두음 머리에 박기 🧠**
> - **벤·성·보·커·기** (로우코드 5대 한계점: **벤**더종속, **성**능한계, **보**안위험, **커**스터마이징한계, **기**술부채)
> - **식·통·상·기·감** (형상관리 기준선과 유사한 SPL 4대 활동처럼, SPL 고려사항 암기용 **도·변·조·초** — **도**메인 범위, **변**동성 관리, **조**직 변화, **초**기 투자)
> - **도·응** (SPL 두 가지 개발 프로세스: **도**메인 공학 Domain Engineering, **응**용 공학 Application Engineering)

---

| 분류 | 기술 기술사 서브노트 작성 예시 (1교시형 포맷) |
| :--- | :--- |
| **토픽명** | **로우코드/노코드 플랫폼(Low Code/No Code)과 소프트웨어 제품계열 방법론(SPL)** |
| **정의** | 시민개발자(Citizen Developer)가 시각적 개발로 애플리케이션을 신속히 생산하는 **로우코드/노코드**와, 공통 핵심 자산(Core Assets)을 기반으로 관련 제품군을 체계적으로 생산하는 **제품계열 방법론(SPL)**은 모두 "재사용 가능한 공통 기반 위에서 빠르게 변형 제품을 생산"한다는 공통 목표를 갖는 개발 생산성 향상 기법 |
| **키워드** | 시민개발자, WYSIWYG, 벤더 종속(Vendor Lock-in), Core Assets, Feature Model, 도메인 공학/응용 공학, 변동성 관리 |
| **개념도** | `[ 로우코드/노코드 플랫폼 ]` ── 시각적 컴포넌트 조립 ──▶ `[ 개별 앱 ]`<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`(공통 UI/로직 블록 재사용)`<br><br>`[ 제품계열 핵심 자산(Core Assets) ]` ── Feature 선택 ──▶ `[ 제품 A / B / C (변형) ]`<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;`(도메인 공학이 자산 구축, 응용 공학이 개별 제품 생산)` |
| **구성요소** | 1. **로우코드/노코드**: 시각적 개발(WYSIWYG), 컴포넌트 기반 조립, API/DB 자동 연동, 자동 코드 생성<br>2. **제품계열 핵심 자산(Core Assets)**: 아키텍처, 컴포넌트, 테스트 케이스, 도메인 모델<br>3. **Feature Model**: 제품군의 공통점(Common)·선택점(Optional)·대안점(Alternative)을 트리 구조로 표현<br>4. **도메인 공학(Domain Engineering)**: 공통 자산·가변점을 미리 구축하는 선행 프로세스<br>5. **응용 공학(Application Engineering)**: Feature 선택을 통해 개별 제품을 조립·생산하는 프로세스 |
| **비교** | **로우코드/노코드 (플랫폼형 재사용)**<br>- **재사용 단위**: UI/로직 블록<br>- **대상**: 시민개발자 포함 광범위<br>- **한계**: 벤더종속, 성능한계, 보안위험, 커스터마이징한계, 기술부채(벤·성·보·커·기)<br><br>**제품계열 방법론 (자산형 재사용)**<br>- **재사용 단위**: 아키텍처·컴포넌트·도메인 모델(Core Assets)<br>- **대상**: 전문 개발 조직(도메인팀/제품팀)<br>- **한계**: 도메인 범위 설정 실패 시 복잡도 폭증, 초기 투자 비용 과다 |
| **차별화** | **공통 기반 재사용 전략을 아우르는 실무 결합 방안**<br>1. **SPL의 Core Assets 위에 로우코드 계층 결합**: 자동차 임베디드 ECU 플랫폼처럼 SPL로 하위 공통 아키텍처를 확정한 뒤, 상위 UI/업무 로직 조립은 로우코드 플랫폼으로 시민개발자에게 위임하여 신차종 SW 개발 기간 단축.<br>2. **거버넌스 이원화**: 로우코드의 섀도우 IT·보안 위험은 CCB(변경통제위원회)형 거버넌스로, SPL의 변동성 폭증은 Feature Model 승인 절차로 각각 통제.<br>3. **테일러링 관점 접근**: 두 기법 모두 표준 개발방법론의 테일러링(맞춤화) 수단으로 활용 가능하며, 프로젝트 특성(신속성 vs 재사용성)에 따라 선택적으로 채택. |
