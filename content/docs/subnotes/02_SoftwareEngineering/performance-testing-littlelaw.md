# 성능 테스트와 리틀의 법칙(Little's Law) 서브노트

> **두음 머리에 박기 🧠**
> - **부·스·내·스** (성능 테스트 4종: **부**하(Load), **스**트레스(Stress), **내**구성(Endurance/Soak), **스**파이크(Spike))
> - **L·λ·W** (리틀의 법칙 구성: **L**=시스템 내 평균 요청 수, **λ**(람다)=단위시간당 유입 처리율(TPS), **W**=평균 체류시간(응답시간) — L=λ×W) |

---

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **소프트웨어 성능 테스트 (Performance Testing) 및 리틀의 법칙 (Little's Law)** |
| **정의** | 부하 상황에서 시스템의 속도(Speed)·확장성(Scalability)·안정성(Stability)을 비즈니스 요구사항 기준으로 검증하는 비기능 테스트로, 대기 이론에 기반한 **리틀의 법칙(L = λ × W)**을 통해 목표 동시 사용자 수와 응답시간으로부터 필요 처리율(TPS)을 수학적으로 도출하여 성능 목표의 객관적 근거를 제공 |
| **키워드** | Little's Law(L=λW), TPS, 부하/스트레스/내구성/스파이크 테스트, Breaking Point, JMeter/Gatling |
| **개념도** | `L = λ × W`<br>&nbsp;&nbsp;&nbsp;&nbsp;예: 목표 동시접속자 L=1,000명, 응답시간 W=2초 → 필요처리율 λ=L/W=500 TPS<br>&nbsp;&nbsp;&nbsp;&nbsp;부하 패턴: `부하테스트`(점진증가 후 유지) / `스트레스테스트`(한계까지 계속 증가) / `내구성테스트`(정상부하 장기 유지, 12~48h) / `스파이크테스트`(급등후 급강하 반복) |
| **구성요소** | 1. **리틀의 법칙 활용**: L(목표 동시사용자)과 W(목표 응답시간)로부터 λ(필요 TPS)를 역산하여 성능 목표를 수학적으로 설정<br>2. **부하 테스트(Load)**: 예상 최대 부하에서 성능 목표 충족 여부 검증<br>3. **스트레스 테스트(Stress)**: 한계점(Breaking Point) 및 최대 처리 용량 파악, Graceful Degradation 여부 확인<br>4. **내구성 테스트(Endurance/Soak)**: 장시간 정상 부하 유지로 메모리 누수·자원 고갈 탐지<br>5. **스파이크 테스트(Spike)**: 급격한 부하 증감에 대한 시스템 회복성 검증<br>6. **핵심 지표**: TPS, 응답시간(P95 기준 SLA), 처리량(Throughput), 한계점, 메모리 누수 |
| **비교** | **JMeter**<br>- **방식**: GUI 기반(XML 설정), 스레드 기반 동시성<br>- **용도**: 전통적 웹 앱, 다양한 프로토콜 지원<br><br>**Gatling**<br>- **방식**: 코드 기반 DSL(Scala/Kotlin), 비동기 이벤트 기반<br>- **용도**: 대규모 부하 시뮬레이션, 내장 HTML 리포트<br><br>**성능 테스트 vs APM(운영 모니터링)**<br>- 성능 테스트: 배포 전 사전 검증 / APM(Datadog·Pinpoint): 운영 중 실시간 모니터링 — 상호 보완 |
| **차별화** | **성능 목표 수립 및 병목 분석 실무 전략**<br>1. **비즈니스 합의 기반 SLA 수립**: Jakob Nielsen의 응답시간 인지 기준(0.1초=즉각, 1초=흐름유지 한계, 10초=집중력 한계)과 도메인 특성을 반영해 이해관계자와 P95 응답시간 기준 SLA를 문서화하고, 리틀의 법칙으로 TPS 목표를 객관적으로 도출.<br>2. **병목 유형 분류 후 최적화**: CPU바운드(알고리즘 최적화·스케일아웃), 메모리바운드(GC튜닝), DB바운드(인덱스·커넥션풀), 네트워크바운드(CDN)로 원인을 분류하고 APM으로 병목 지점을 먼저 확정한 뒤 최적화하는 순서 준수.<br>3. **스트레스 테스트의 우아한 성능 저하 검증**: 한계 초과 시 시스템이 완전히 죽는지, 일부 기능만 제한하며 서비스를 유지하는 Graceful Degradation을 하는지 확인해 장애 대응 설계에 반영. |
