# ITA 기반 H/W 용량산정 서브노트

> **두음 머리에 박기 🧠**
> - **피·목·동·트·데** (H/W 용량산정 5대 결정점: **피**크배율, **목**표CPU활용률, **동**시사용자수, **트**랜잭션당 자원소비량, **데**이터증가율)
> - **서·스·네** (규모산정 3대 대상: **서**버(Web·WAS·DB), **스**토리지(데이터·백업·아카이브), **네**트워크(스위치·방화벽))

---

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **ITA(정보기술아키텍처) 기반 H/W 용량산정 (Capacity Planning)** |
| **정의** | 목표 시스템의 업무 처리 능력 요구사항을 만족시키는 CPU·Memory·Storage·Network의 최소 필요 규모를 정량적으로 도출하는 프로세스로, ITA 기반 공공 사업에서는 산정 결과가 예산 편성의 공식 근거가 됨 |
| **키워드** | TPS, 피크 배율, 목표 CPU 활용률, tpmC(TPC-C), IOPS, 클라우드 오토스케일링 |
| **개념도** | `[업무 요구사항 분석]`(일 최대 트랜잭션, 동시사용자) → `[TPS 산정]`(=일 최대 거래건수÷유효시간×피크배율) → `[자원별 용량 계산]`(CPU/Memory/Disk) → `[여유율·이중화 반영]`(N+1, DR) → `[최종 H/W 사양 결정]` |
| **구성요소** | 1. **CPU 용량**: 필요CPU = TPS × 트랜잭션당 CPU처리시간 ÷ 목표CPU활용률(통상 60~70%)<br>2. **Memory 용량**: 동시사용자수×세션당메모리 + OS/WAS/DB버퍼 + 여유(20~30%)<br>3. **Disk 용량**: 초기데이터 + (연간증가량×보존기간) + 인덱스(20~30%) + RAID 오버헤드 × 여유율(1.2~1.5)<br>4. **규모산정 대상**: 서버(Web·WAS·DB·배치/연계), 스토리지(데이터·백업·아카이브), 네트워크(L4스위치·방화벽·IDS/IPS)<br>5. **성능 기준지**: tpmC(TPC-C 기준 분당 신규주문 트랜잭션, CPU 성능비교), IOPS(초당 I/O 작업수, 스토리지 성능기준), 처리량(MB/s), 응답시간(ms) |
| **비교** | **On-Premise 용량산정**<br>- **산정 단위**: 서버 대수·코어 수·GB (수직 확장 Scale-up 중심)<br>- **비용 구조**: 초기 CAPEX 집중, 피크 기준 과잉 프로비저닝<br><br>**클라우드(IaaS/PaaS) 용량산정**<br>- **산정 단위**: 인스턴스 유형(t3.xlarge 등), 수평 확장(Scale-out) 용이<br>- **비용 구조**: 사용량 기반 OPEX, 오토스케일링 탄력 대응 — 다만 기준 인스턴스(Baseline) 선정을 위한 초기 용량산정은 클라우드에서도 필수 |
| **차별화** | **비용 통제와 정확도 향상을 위한 용량산정 실무 전략**<br>1. **기준 인스턴스+오토스케일링 이중 접근**: 클라우드에서도 Baseline 인스턴스 산정 후 오토스케일링 Upper bound(비용 상한)를 함께 설정하여 무분별한 인스턴스 증가로 인한 예산 통제 불능 방지.<br>2. **2단계 피크 배율 검증**: 유사 도메인 트래픽 패턴 참조로 초기 산정 후, 부하 테스트(Load Test) 결과로 산정값을 재검증하여 신규 시스템의 주관적 산정 오류를 최소화.<br>3. **Year 1/Year 2~3 분리 구성**: 3년 증가분을 초기에 모두 프로비저닝하지 않고 초기 구축비 과다·낮은 활용률 문제를 방지하며, 클라우드는 오토스케일링, On-Premise는 블레이드 서버 증설로 단계적 확장. |
