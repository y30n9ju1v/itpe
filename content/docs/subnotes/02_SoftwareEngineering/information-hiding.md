# 소프트웨어 설계 원리 서브노트

> **두음 머리에 박기 🧠**
> - **추·정·단·모** (SW 4대 설계 원리 순서: **추**상화 → **정**보은닉 → **단**계적분해 → **모**듈화)
> - **P·R·P·P** (접근 제어자 4종: **P**rivate, package(default), **P**rotected, **P**ublic — 범위가 좁은 순)
> - **변·결·재·보·테** (정보은닉의 5대 장점: **변**경 용이성, **결**합도 감소, **재**사용성, **보**안성, **테**스트 용이성)
> - **기·순·통·절·시·논·우** (응집도 강한순: **기**능적>**순**차적>**통**신적>**절**차적>**시**간적>**논**리적>**우**연적)
> - **자·스·제·외·공·내** (결합도 약한순: **자**료<**스**탬프<**제**어<**외**부<**공**통<**내**용)

| 항목 | 내용 |
| :--- | :--- |
| **토픽명** | **소프트웨어 설계 4대 원리 (추상화·정보은닉·단계적분해·모듈화)** |
| **정의** | SW 개발 시 복잡성을 관리하고 품질을 확보하기 위한 4대 설계 원칙으로, 핵심 본질만 추출하는 **추상화**, David Parnas가 1972년 제안한 원칙으로 모듈 내부 구현을 인터페이스 뒤로 은폐하는 **정보은닉**, 상위→하위로 점진 분할하는 **단계적 분해**, 독립된 SW 단위로 형상화하는 **모듈화**가 순서대로 유기적으로 연결되어 유지보수성·재사용성의 기반을 형성 |
| **키워드** | 추상화(기능/자료/제어), Parnas 정보은닉, 단계적분해(Top-Down), 모듈화(응집도/결합도), 캡슐화, Repository 패턴 |
| **개념도** | `[복잡한 현실 문제]` → `추상화`(핵심 본질만 추출) → `정보은닉`(세부 구현 은폐, 인터페이스만 공개) → `단계적분해`(상위→하위 점진 분할) → `모듈화`(독립 SW 단위로 형상화)<br>&nbsp;&nbsp;&nbsp;&nbsp;`[ 외부 호출자 ]` ── 인터페이스(public)로만 접근 ──▶ `[ 모듈 공개 인터페이스 ]` → `▼(내부 은닉)` → `[ 변경 가능성 높은 내부 구현(private) ]` |
| **구성요소** | 1. **추상화(Abstraction)**: 기능/자료/제어 추상화로 불필요 특성 제거, 복잡성 감소 (예: `obj.getName()`)<br>2. **정보은닉(Information Hiding)**: 캡슐화(무엇을 묶을지)의 수단으로 내부 구현을 은폐(어떻게 감출지); 접근제어자 private(클래스 내부)/protected(상속)/package(동일패키지)/public(전체공개)<br>3. **단계적 분해(Stepwise Refinement)**: 하향식(Top-Down)으로 추상화 수준별 점진 분할, 복잡성 분할 관리<br>4. **모듈화(Modularization)**: 응집도↑/결합도↓ 기준으로 재사용성·유지보수성 향상 (응집도: 기능적>순차적>통신적>절차적>시간적>논리적>우연적, 결합도: 자료<스탬프<제어<외부<공통<내용)<br>5. **정보은닉 위반 사례**: public 필드 직접 노출, 로직 없는 getter/setter 남용, 구현 클래스를 반환 타입으로 노출 |
| **비교** | **추상화 (Abstraction) vs 정보은닉 (Information Hiding)**<br>- 추상화: 불필요 특성 제거, 핵심 본질만 파악 (기능/자료/제어 추상화)<br>- 정보은닉: 내부 구현을 외부로부터 은폐 (캡슐화/인터페이스 정의)<br><br>**단계적 분해 (Stepwise Refinement) vs 모듈화 (Modularization)**<br>- 단계적 분해: 상위→하위 점진 분할, 하향식(Top-Down), 복잡성 분할 관리<br>- 모듈화: 독립된 SW 단위 구성, 응집도·결합도·Fan-In/Out 측정<br><br>**캡슐화 (Encapsulation) vs 정보은닉**<br>- 캡슐화: 데이터와 행위를 하나의 단위로 묶는 것(목적) / 정보은닉: 묶인 내부를 외부에서 볼 수 없게 하는 것(수단) |
| **차별화** | **설계 원리의 현대적 재해석 및 아키텍처 확장 적용 전략**<br>1. **MSA로의 현대적 재해석**: 추상화는 Open API, 정보은닉은 DB-per-Service, 모듈 단위는 독립 배포 서비스로 재해석되며, 품질 척도인 응집도/결합도는 서비스 간 느슨한 결합으로 계승.<br>2. **Repository 패턴을 통한 DB 교체 유연성 확보**: DB 접근 로직을 인터페이스 뒤에 은닉하여 MySQL→NoSQL 전환 시 호출자 코드 무변경으로 마이그레이션 리스크 최소화.<br>3. **과도한 추상화(Over-Engineering) 경계**: YAGNI 원칙을 병행해 변화가 확실한 임계 영역에만 선택적으로 고차원 추상화를 도입하고, 모듈 세분도는 통합 비용(Integration Cost)과의 트레이드오프를 고려해 SW 생명주기 총비용이 최저가 되는 지점으로 산정. |
